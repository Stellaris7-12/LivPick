# Redis宕机恢复

## 1. 先回答结论

如果面试官问“Redis 宕机了怎么办”，不能只回答“重启 Redis”或者“做主从切换”，而应该分层次回答：

1. 事前：高可用架构设计
2. 事中：监控告警、降级、限流、熔断
3. 事后：故障恢复、数据校验、流量回放

也就是说，这个问题本质上不是单点技术题，而是一个完整的稳定性题。

所以，**是的，应该从高可用架构、监控、降级、限流、熔断这些方面一起阐述。**

---

## 2. 先讲高可用架构

## 2.1 为什么 Redis 不能单机扛生产

如果 Redis 是单机部署，那么一旦宕机，会直接影响：

- 缓存读写
- 秒杀库存校验
- 分布式锁
- 延迟队列
- 布隆过滤器
- 登录态

所以单机 Redis 只适合开发环境，不适合生产环境。

---

## 2.2 生产环境怎么做高可用

对于这个项目，Redis 高可用建议分两档讲。

### 第一档：主从 + Sentinel

这是当前项目最适合的第一阶段生产方案：

- 1 主
- 2 从
- 3 Sentinel

这样做的好处是：

- 主节点负责写
- 从节点负责备份和可选读扩展
- Sentinel 负责监控、故障发现和自动切换

如果主节点挂了，Sentinel 会选举新的主节点，客户端通过新的主节点继续服务。

### 第二档：Redis Cluster

如果后续继续增长，出现：

- 数据容量过大
- 单节点内存瓶颈
- QPS 明显超过单主承载能力

再进一步升级到 Redis Cluster。

所以更稳妥的表达是：

**当前项目生产阶段优先做主从 + Sentinel 保高可用，容量和吞吐进一步增长后再演进到 Cluster。**

---

## 2.3 为什么不是一上来就说 Redis Cluster

因为 Redis 宕机恢复和 Redis 扩容不是一回事。

如果面试官问的是“Redis 挂了怎么办”，你首先要解决的是：

- 高可用
- 自动故障转移
- 服务连续性

这时候优先讲：

- 主从复制
- Sentinel

会更自然。

Cluster 更偏向：

- 分片
- 横向扩容
- 大容量

它也有高可用能力，但不是回答“宕机怎么办”的第一层重点。

---

## 3. 再讲监控和告警

高可用架构只是第一步，不做监控，故障仍然会被动。

Redis 需要重点监控以下指标：

- Redis 实例存活状态
- 主从复制延迟
- 内存使用率
- 命中率
- 连接数
- QPS
- 慢查询
- AOF / RDB 持久化状态
- Sentinel 状态

如果是这个项目，还要补充业务维度监控：

- 秒杀接口失败率
- 缓存命中率
- 布隆过滤器拦截率
- Kafka 消息堆积
- Redis 锁获取失败率

你可以这样说：

“Redis 宕机恢复不是只盯 Redis 进程本身，我还会把业务指标一起监控，因为很多时候先暴露出来的是业务失败率升高，而不是底层实例直接报警。”

---

## 4. Redis 宕机后系统应该如何降级

即使有高可用，也不能假设 Redis 故障永远瞬间恢复。  
所以 Redis 不可用时，业务系统要能降级。

对于这个项目，可以分场景讲。

### 4.1 缓存场景降级

如果 Redis 是缓存层，Redis 宕机后最直接的问题是缓存失效，流量会回源到 MySQL。

这时候要做的降级策略是：

- 只保留核心查询能力
- 非核心接口降级或限流
- 热点接口做流量削峰

比如：

- 店铺详情还能查，但响应可能变慢
- 排行榜、推荐流、非关键统计类能力可以临时关闭

### 4.2 秒杀场景降级

这个项目里 Redis 不只是缓存，还是秒杀资格校验核心组件。  
如果 Redis 宕机，秒杀链路不能继续正常放量。

这时候更合理的做法是：

- 暂停秒杀入口
- 对秒杀接口直接返回“活动火爆，请稍后重试”
- 或者把流量切到排队页/降级页

不能在 Redis 挂掉后直接把所有秒杀请求打到数据库，否则数据库会被击穿。

### 4.3 登录态场景降级

如果 Redis 还承载登录态，那么 Redis 宕机时可能影响登录和鉴权。

这时候可以考虑：

- 已登录用户短时间容忍本地缓存 token
- 暂时限制新的登录请求
- 对非核心接口开放匿名读

当然这取决于系统设计，但面试时可以说明：

“Redis 承担不同角色时，降级策略是不同的，缓存可以回源，秒杀要熔断，登录态要谨慎放行。”

---

## 5. 限流该怎么讲

Redis 宕机时，最危险的一件事是：

**原本被 Redis 挡住的流量，全部打到数据库和应用。**

所以必须限流。

限流可以从三层讲：

### 5.1 网关层限流

比如：

- Nginx
- API Gateway
- Sentinel / 网关限流组件

作用是第一时间挡住突发流量。

### 5.2 应用层限流

在应用服务里，对热点接口做：

- 令牌桶
- 漏桶
- 固定窗口 / 滑动窗口

尤其是：

- 秒杀接口
- 店铺热点查询
- 登录接口

### 5.3 业务层限流

比如：

- 秒杀活动直接排队
- 只放固定比例流量进入后端
- 某些非核心功能临时关闭

面试时可以总结成一句：

“Redis 宕机后限流的目标不是优化体验，而是保护后端数据库和应用不被连带打挂。”

---

## 6. 熔断该怎么讲

熔断的重点不是“慢一点”，而是“先停下来，避免雪崩”。

### 6.1 哪些能力应该熔断

对于这个项目，Redis 挂掉后，以下能力应该优先考虑熔断：

- 秒杀下单
- 高频热点查询
- 依赖 Redis 锁的关键链路
- 依赖 Redis 延迟队列的非实时任务入口

### 6.2 熔断后的返回策略

常见做法：

- 返回固定错误提示
- 返回兜底静态数据
- 返回“系统繁忙，请稍后再试”
- 引导用户进入排队页

特别是秒杀场景，正确做法不是“继续硬扛”，而是：

- 快速失败
- 主动拒绝请求
- 保护数据库和消息链路

---

## 7. Redis 宕机后的恢复流程怎么讲

这一部分是很多人容易漏掉的。

Redis 恢复不是“服务拉起来就结束”，还要考虑数据和状态是否一致。

### 7.1 基础恢复

如果是主从 + Sentinel：

1. Sentinel 发现主节点不可用
2. 选举新主
3. 客户端切换到新主
4. 服务逐步恢复

如果是单机：

1. 重启 Redis
2. 根据 RDB/AOF 恢复数据
3. 应用重新连接

### 7.2 数据一致性校验

对这个项目来说，Redis 里可能存放的是：

- 秒杀预扣库存
- 用户下单资格
- 缓存数据
- 布隆过滤器
- 延迟队列消息

所以恢复后不能默认这些数据完全正确，应该做校验。

比如：

- 对比 MySQL 和 Redis 的库存
- 校验未支付订单与延迟队列是否一致
- 检查布隆过滤器是否需要重建
- 检查缓存热点 key 是否需要预热

### 7.3 业务补偿

如果 Redis 在故障期间丢了部分状态，需要补偿。

比如：

- 秒杀库存重新装载
- 用户资格集合重新构建
- 布隆过滤器重建
- 热点缓存预热

对于当前项目，面试时可以直接说：

“Redis 恢复后我会先以 MySQL 作为最终事实源，对库存、订单状态和缓存数据做一次对账和修复。”

---

## 8. 结合当前项目，完整回答模板

如果面试官直接问：

### “Redis 宕机了怎么办？”

你可以这样答：

“这个问题我会分三层处理。第一层是事前高可用设计，生产环境不会用单机 Redis，而是先采用主从加 Sentinel，后续容量和吞吐继续上来再演进到 Redis Cluster。第二层是事中保护，Redis 挂掉后不能让流量直接打穿数据库，所以要结合监控告警、接口降级、限流和熔断。比如缓存场景可以做回源和降级，秒杀场景要直接限流甚至熔断，避免数据库被击穿。第三层是事后恢复，Redis 恢复后不能只看进程活了没，还要做数据对账和补偿，比如以 MySQL 作为最终事实源，重新校验库存、订单状态、布隆过滤器和热点缓存。” 

如果他继续追问“这个项目里 Redis 挂了最危险的是什么”，你可以补一句：

“最危险的是秒杀场景，因为 Redis 在这里不只是缓存，还承担库存和一人一单校验。如果 Redis 挂了，不能把秒杀请求直接放到数据库，而是应该快速降级或熔断秒杀入口。” 

---

## 9. 面试时建议的结构化表达

最稳的顺序是：

1. 先讲高可用架构
2. 再讲监控告警
3. 再讲降级、限流、熔断
4. 最后讲恢复后的数据对账和补偿

也就是说，这道题不是只答：

- Redis 主从
- Redis Cluster

而是要体现你有完整的稳定性思维。

---

## 10. 一句话收口

你可以用这句话结束：

“Redis 宕机恢复不能只从中间件本身去看，而要从高可用架构、监控告警、限流熔断、业务降级和数据补偿几个层面一起设计，尤其像这个项目里 Redis 还承担秒杀校验和 Redisson 能力时，故障处理一定要按业务优先级分级响应。”
