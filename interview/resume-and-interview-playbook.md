# 简历描述与数据口径说明

## 简历描述

高并发秒杀系统 后端开发  
2025.XX - 2025.XX

项目简介：基于黑马点评项目完成高并发秒杀链路重构，围绕防超卖、一人一单、异步削峰、超时关单、库存回补、缓存穿透/击穿治理与缓存一致性，推动系统从 `MySQL-only` 演进到 `Redis + Kafka + Redisson` 的异步秒杀架构，形成支持高并发抢购的完整业务闭环。  
技术栈：`Java`、`Spring Boot`、`MySQL`、`Redis`、`Lua`、`Kafka`、`Redisson`、`MyBatis-Plus`

项目亮点：
- 设计 `Redis + Lua` 原子化秒杀资格校验与库存预扣方案，前置拦截库存不足和重复下单请求；在 `flash-sustain` 压测场景下，使用 `500` JMeter 线程持续压测 `60s`，秒杀接口入口吞吐稳定在 `577~585 req/s`，`3.4w+` 总请求中最终仅 `100/500` 个进入成功链路，并实现 `0` 超卖、`0` 重复有效订单。
- 引入 `Kafka` 异步削峰与订单落库机制，将成功请求处理链路从同步写库改造成可排队、可补偿、可恢复的异步闭环，补齐 pending-send 重试、重复消费兜底、订单取消后库存与资格恢复、取消订单复用再次抢购等状态机逻辑。
- 基于 `Redisson` 延迟队列 + `Spring Task` 兜底实现未支付订单自动关单；在 `100 单 / 15 秒超时` 的统一口径下，将自动关单 `P95` 延迟从 `4055ms` 降至 `533ms`，时效提升约 `86.9%`。
- 采用 `RBloomFilter + 缓存空值` 解决缓存穿透，使用逻辑过期方案缓解热点 Key 击穿；在纯非法 `shopId` 请求场景下，将数据库回源次数从 `26` 次降至 `0`，查询 `P95` 从 `114ms` 优化到 `91ms`。
- 采用旁路缓存模式保证缓存一致性：更新数据库后删除缓存，若删除失败则发送 MQ 做补偿重试，并通过 TTL 兜底，降低脏缓存长期残留风险。

## 数据口径说明

这一节专门解释简历里涉及的几个数字，避免面试时被追问口径。

### 1. “5k 总并发”这个说法怎么理解

更准确的说法不是“5k 并发线程”，而是：

- `flash-sale` 是按 **5k 级抢购活动规模**命名的场景
- 场景里使用了 `50000` 个唯一用户 ID 数据集
- 其中重点场景是：
  - `flash-sustain-5k-100`
  - `flash-sustain-5k-500`
  - `flash-burst-5k-100`
  - `flash-burst-5k-500`

但正式压测时，JMeter 并不是直接起 `5000` 个线程：

- `flash-sustain`
  - 线程数：`500`
  - Ramp-Up：`5s`
  - 持续时间：`60s`
- `flash-burst`
  - 线程数：`1000`
  - Ramp-Up：`3s`
  - 持续时间：`10s`

所以更稳妥的面试说法应该是：

“我做的是 `5k` 级秒杀活动口径压测，但正式脚本里 `flash-sustain` 使用 `500` 线程持续压测、`flash-burst` 使用 `1000` 线程做短时突刺，不是直接起 `5000` 个压测线程。”

### 2. `3.4w+` 总请求是怎么来的

`3.4w+` 是 JMeter 在压测窗口内累计打到 `/voucher-order/seckill/{voucherId}` 的总请求量，不是成功请求数。

以正式结果为例：

- `flash-sustain-5k-100`
  - Samples：`34916`
  - 最终成功受理：`100`
- `flash-sustain-5k-500`
  - Samples：`34490`
  - 最终成功受理：`500`

也就是说：

- 请求总量是 `3.4w+`
- 真正进入成功链路的是库存量级 `100/500`
- 其余请求大多在 `Redis + Lua` 层因为库存不足被快速拒绝

### 3. “500+ req/s”是什么意思，是不是 QPS

这里的 `500+ req/s` 本质上就是压测入口吞吐，可以近似理解为 HTTP 接口层面的 QPS。

但更准确的说法是：

- 这是 **秒杀接口入口吞吐**
- 统计位置是 `POST /voucher-order/seckill/{id}`
- 不是数据库吞吐
- 也不是 Redis 原生命令吞吐

脚本里的计算方式是：

- `Throughput = Samples / 压测窗口总秒数`

对应脚本：
- [run-jmeter-benchmark.ps1](/C:/Users/heyunhui/IdeaProjects/LivPick-db-cache-mq/benchmark-final/suites/db-cache-mq/flash-sale/run-jmeter-benchmark.ps1)

所以面试时建议说：

“`500+ req/s` 是秒杀 HTTP 接口入口吞吐，不是数据库 QPS，也不是 Redis QPS。”

### 4. 为什么这个 `500+ req/s` 看起来不高

这个质疑是合理的，不能硬拗。

原因主要有 4 个：

1. 当前是单机环境
- 单应用
- 单 Redis
- 单 Kafka broker
- 单 partition

2. Kafka 生产端还是半同步
- 当前发送秒杀消息时用了 `kafkaTemplate.send(...).get(5, TimeUnit.SECONDS)`
- 也就是接口线程仍然要等待 broker ack
- 这会明显抬高入口 RT，压低入口吞吐

3. Kafka 消费端是单通道重事务消费
- `1 partition` 基本意味着秒杀消息消费天然单通道
- 每条成功消息都要执行完整事务：
  - 分布式锁
  - 查订单
  - 扣 DB 库存
  - 写订单
  - 投递超时消息

4. 当前结论强调的是“削峰闭环”，不是“极限 Redis QPS”
- 这个架构的核心价值是：
  - 绝大多数无效请求在 Redis 前置失败
  - 少量成功请求异步落库
  - 库存、订单、资格状态最终一致

所以这套数据不能表述成“我的 Redis 极限性能很高”，而应该表述成：

“在单机、单 broker、单 partition 的保守配置下，系统完成了秒杀前置过滤、异步削峰和最终一致性闭环；当前入口吞吐不是这套架构的极限，更受 Kafka 同步发送和单通道消费约束。”

### 5. 自动关单为什么用了 Redisson 之后还有 `533ms` 延迟

这个 `533ms` 指的是：

- 订单理论超时时刻
- 到系统真正完成关单

之间的 `P95` 延迟，不是“创建订单到关单总耗时”。

之所以不是接近 `0ms`，主要有 4 个原因：

1. 延迟队列不是实时中断触发
- `RDelayedQueue` 到期后仍然要转移到 `RBlockingDeque`
- 消费线程再 `take()` 出来处理

2. 消费线程不是零开销
- 取消息
- 反序列化
- 查订单
- 乐观更新订单状态
- 回补 DB 库存
- 执行 Redis 回补 Lua

3. JVM 线程调度和 Redis 网络往返有固定成本
- 在单机开发环境里，几百毫秒级的尾延迟是正常现象

4. `P95` 本来就是尾延迟
- 它不是平均值
- 本轮结果里 `P50` 已经只有 `26ms`
- 说明大多数订单关得很快，主要是尾部样本把 `P95` 拉到了 `533ms`

所以更合适的表述是：

“Redisson 延迟队列已经把关单时效从秒级扫描等待压到了亚秒级尾延迟，`P50=26ms`、`P95=533ms`，说明大多数订单几乎在到期后立即关闭，尾延迟主要来自队列投递、消费线程调度和数据库回补成本。”

### 6. 为什么纯非法请求场景下 DB 回源只有 `26` 次

这个问题也很关键。

因为当前对照场景不是“每次非法请求都一定打 DB”，而是：

- `OFF` 模式：关闭 BloomFilter，但仍然保留缓存空值方案

这意味着：

1. 第一次访问某个非法 `shopId`
- 会 miss Redis
- 走一次 DB 回源
- 然后写入空值缓存

2. 后续大量相同非法请求
- 直接命中空值缓存
- 不再回源 DB

所以在当前纯非法单 ID 场景里：

- `OFF` 模式下 DB 回源不是几万次
- 而是少量“空值缓存失效窗口内”的回源
- 最终统计到 `26` 次

而 `BLOOM_NULL` 模式下：

- 请求在 BloomFilter 就被挡掉了
- 因此 DB 回源变成 `0`

这组数据的意义不是“把几万次 DB 查询降到 0”，而是：

- 证明 **在已有空值缓存的前提下**
- BloomFilter 还能进一步把首次非法探测和空值失效窗口的 DB 回源压到 0
- 同时减少 Redis 查询链路，提升 `P95`

所以这个点在简历里更适合写成：

“在纯非法请求场景下，`RBloomFilter + 缓存空值` 将 DB 回源从少量窗口性回源压降为 `0`，并将查询 `P95` 从 `114ms` 优化到 `91ms`。”

不要写成“拦住了几万次数据库攻击”，那样会被追问穿。

## Kafka、Pending Message 和 `seckill:reorder` 说明

### 1. 当前 Kafka 投递与消费逻辑

秒杀主链路现在的实际流程是：

1. 用户请求 `/voucher-order/seckill/{voucherId}`
2. 服务端先查 `seckill:reorder:{voucherId}:{userId}`
   - 看这个用户是否有已取消但可复用的旧订单 ID
3. 执行 `seckill.lua`
   - 校验 `seckill:stock:{voucherId}`
   - 校验 `seckill:order:{voucherId}`
   - Redis 预扣库存
   - 记录用户已占用资格
4. Lua 成功后组装 `SeckillOrderMessage`
5. 先把消息注册到 Redis pending-send
6. 再发 Kafka
7. Kafka 成功则清理 pending
8. Kafka 失败则保留 pending，交给定时任务补发
9. Kafka Consumer 收到消息后，在 `Redisson lock:order:{userId}` 下异步落库

### 2. Pending Message 相关 Redis key 是干什么的

核心有两类：

- `seckill:pending:send:{orderId}`
  - 保存待补发消息详情
- `seckill:pending:send:index`
  - ZSet 索引
  - member 是 `orderId`
  - score 是 `nextRetryAt`

这套设计的作用是：

1. 下单资格已经在 Redis 预占成功
2. 但 Kafka 首发可能失败
3. 如果这时没有 pending 记录，就会出现：
   - Redis 已扣库存
   - 但消息没投出去
   - 最终也没人落库

所以 pending-send 本质是一个“**投递前登记、投递失败可补发**”的轻量 Outbox 近似方案。

### 3. 这个 pending 方案高效吗

从正确性上说，它是有效的。  
从性能和工程成熟度上说，它不是最优。

优点：
- 实现简单
- 解决了“Redis 已预占但 Kafka 首发失败”的一致性缺口
- 面试上很好讲

缺点：
- 本质还是 Redis 明细 key + ZSet 扫描
- 不是数据库事务型 Outbox
- 扫描频率固定 `5s`
- batch size 只有 `20`
- 堆积很多时补偿吞吐一般

所以更准确的评价是：

“它是一个在项目场景里足够实用的轻量补偿方案，优先保证不丢成功请求，但不是企业里最重型、最标准的事务消息方案。”

### 4. `seckill:reorder` 是干什么的

`seckill:reorder:{voucherId}:{userId}` 的作用是：

- 记录这个用户对这张券最近一次“已取消订单”的 `orderId`

它解决的问题是：

- 你保留了数据库唯一索引 `uk(voucher_id, user_id)`
- 但又希望“超时取消后允许再次抢购”

这两个需求直接冲突：

- 如果不复用旧订单，用户再次抢购时会因为唯一索引无法插入新订单
- 如果删历史单再重建，状态链路又会更复杂

所以当前做法是：

1. 超时取消时
   - 恢复库存
   - 恢复 `seckill:order:{voucherId}` 里的资格
   - 写入 `seckill:reorder:{voucherId}:{userId}=orderId`

2. 用户再次秒杀时
   - 先读这个 key
   - 如果存在，就复用原 `orderId`

3. Consumer 落库时
   - 如果查到数据库已有 `CANCELLED` 且 `id == message.orderId`
   - 就把原订单重置为 `UNPAID`

### 5. 这种权限恢复方案高效吗

从当前项目目标看，它是高效且实用的。

优点：
- 不需要放开 `(voucher_id,user_id)` 唯一索引
- 不需要多建一张“抢购资格表”
- 不需要每次秒杀前同步查数据库决定是否可重购
- 资格恢复和订单复用逻辑都放在 Redis + 异步消费里完成，链路比较顺

缺点：
- 方案明显带有“项目实现痕迹”，不是最通用的企业模板
- Redis 里多维护一个 `reorder` 标记
- 需要 Consumer 分支支持“重激活取消订单”

### 6. 这是不是企业主流方案

严格说，不算主流通用方案。

企业里更常见的做法通常有 3 类：

1. 允许同用户同券有多条历史订单
- 通过“当前有效订单唯一”或状态机约束来控制

2. 单独维护抢购资格或预约记录表
- 订单只是结果，不直接承担全部资格语义

3. 更重的事务消息 / Outbox / Saga 方案
- 用于做状态变更和补偿编排

你现在这套 `reorder` 方案的定位更适合这样讲：

“这是一个为了兼容唯一索引、一人一单语义和取消后可重购需求而设计的工程化折中方案。它不是最通用的企业标准模板，但在当前项目里实现成本低、链路清晰、正确性可验证，适合展示我对状态机闭环和补偿逻辑的思考。”
