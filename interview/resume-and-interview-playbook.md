# 秒杀项目描述重构与面试话术

## 1. 简历项目描述重构

高并发秒杀系统 后端开发  
2025.XX-2025.XX

项目简介：基于黑马点评项目完成高并发秒杀链路重构，围绕防超卖、一人一单、异步削峰、超时关单、库存回补与缓存一致性，推动系统从 `MySQL-only` 演进到 `Redis + Kafka` 异步秒杀架构，形成支持高并发抢购的完整业务闭环。  
技术栈：`Java`、`Spring Boot`、`MySQL`、`Redis`、`Lua`、`Kafka`、`Redisson`、`MyBatis-Plus`

项目亮点：

- 设计 `Redis + Lua` 原子化秒杀资格校验与库存预扣方案，前置拦截库存不足和重复下单请求；在 `5k` 并发压测下，秒杀入口吞吐稳定在 `500+ req/s`，`3.4w+` 总请求最终仅 `100/500` 个进入成功链路，并实现 `0` 超卖、`0` 重复有效订单。
- 引入 `Kafka` 异步削峰与订单落库机制，将成功请求处理链路从同步写库改造成可排队、可补偿、可恢复的异步闭环，保证异步链路最终排空，库存与订单最终一致，完成秒杀主链路状态机闭环。
- 基于 `Redisson` 延迟队列 + `Spring Task` 兜底实现未支付订单自动关单，支持订单取消后库存与购买资格恢复，以及原订单复用再次抢购；压测下自动关单 `P95` 延迟从 `4055ms` 降至 `533ms`，时效提升约 `86.9%`。
- 使用乐观锁解决支付回调与超时关单并发冲突，避免订单状态覆盖和重复回补库存，确保支付与关单并发场景下的数据准确性。
- 采用布隆过滤器 + 缓存空值解决缓存穿透，使用逻辑过期缓解热点 Key 击穿；在纯非法请求场景下将数据库回源从 `26` 次降至 `0`，查询 `P95` 从 `114ms` 优化到 `91ms`，并通过旁路缓存 + MQ 补偿重试 + TTL 兜底保障缓存与数据库最终一致性。

## 2. 项目亮点怎么讲

### 2.1 最推荐的开场方式

这个项目我不是只做了一个“能跑的秒杀接口”，而是围绕高并发秒杀场景，完整做了一次架构演进。最开始是 `MySQL-only`，瓶颈在数据库热点库存行竞争；第二阶段引入 `Redis + Lua`，把大量失败请求提前拦在缓存层；第三阶段又继续引入 Kafka，把成功请求从同步写库改造成异步削峰和最终落库。后面我还补了未支付订单自动关闭、库存回补、支付与关单并发控制、缓存穿透和缓存一致性这些业务闭环，最后还做了三套架构的压测对比。

### 2.2 一句话亮点总结

- `MySQL-only` 解决“能下单”
- `db-cache` 解决“高并发下别把数据库打挂”
- `db-cache-mq` 解决“成功请求怎么异步消化，并把状态机和补偿闭环补完整”

## 3. 三种架构演进怎么讲

### 3.1 第一阶段：MySQL-only

可以这样说：

最开始我先保留了最直接的同步下单方案，所有请求直接走数据库扣库存和创建订单。这一版逻辑最简单，但问题也最明显：高并发下大量请求都会冲击同一行库存数据，数据库热点竞争非常严重，失败请求也会持续占用数据库连接和事务资源。

### 3.2 第二阶段：db-cache

可以这样说：

第二阶段我把核心优化放在入口过滤。通过 `Redis + Lua` 在缓存层完成库存判断和一人一单校验，让大量本来就不可能成功的请求直接在 Redis 层失败返回，不再继续打到数据库。这个阶段最大的收益是降低数据库热点写竞争，所以从本机单节点压测结果看，`db-cache` 在高反差秒杀场景下的入口吞吐是最强的。

### 3.3 第三阶段：db-cache-mq

可以这样说：

但我后来发现，`db-cache` 只能解决失败请求过滤的问题，真正成功的请求仍然是同步写库。于是我继续把成功链路改造成 `Redis 预占资格 + Kafka 异步落库`。这样前台接口只负责资格判断和消息投递，后台再异步完成扣减数据库库存和创建订单。同时我补了 pending-send 补偿、超时关单、库存与资格回补、取消后复用原订单再次抢购等逻辑，把业务状态机真正闭环。

## 4. 怎么解释压测结论

### 4.1 最重要的说法

不要说“引入 MQ 后本机 QPS 一定最高”，因为这和你的真实数据不完全一致。  
更准确的说法是：

- 如果只看当前单机、单 Redis、单 Kafka broker、单 partition 下的入口吞吐，`db-cache` 是最强的。
- 但 `db-cache-mq` 的价值不只是更高的入口 QPS，而是把成功请求从同步写库改造成了可恢复、可补偿、可观测的异步闭环。

### 4.2 结合真实数据怎么说

推荐这样表达：

我重点看的是高反差秒杀场景，也就是库存很小、请求很多的时候。比如在 `5k` 并发、库存 `100/500` 的场景里，`db-cache-mq` 总请求量到了 `3.4w+`，但最终真正进入成功链路的只有 `100/500` 个请求，其他请求都在 Redis + Lua 层被快速拦截掉了，最后库存归零、订单数与库存严格一致。这说明系统完成了秒杀削峰和最终一致性的闭环。

### 4.3 为什么 `db-cache-mq` 还能说是最终架构

推荐这样表达：

`db-cache` 的优势主要在入口过滤，但成功请求还是同步写库。  
`db-cache-mq` 在这个基础上继续解决了成功请求异步消化、消息补偿、超时关单、库存回补和状态恢复问题，所以从工程完整度看，它是更合理的终态架构。

## 5. 面试时常见追问

### 5.1 为什么要用 Lua 脚本

回答思路：

- 秒杀资格校验涉及两个条件：库存是否充足、用户是否已经下过单。
- 如果用多条 Redis 命令分别执行，会有并发竞争窗口。
- Lua 脚本能把库存判断、资格判断、扣减库存和写用户标记做成原子操作，避免超卖和并发重复下单。

### 5.2 为什么 `db-cache` 入口吞吐比 `db-cache-mq` 还高

回答思路：

- 当前压测环境是单机、单 Redis、单 Kafka broker、单 partition。
- 这种配置下，Kafka 的横向并行能力没有真正展开，反而会引入消息投递和消费调度成本。
- 所以单看入口吞吐，`db-cache` 更强是合理的。
- 但 `db-cache-mq` 解决的是成功请求如何异步消化和恢复的问题，重点不只是一个入口 QPS 数字。

### 5.3 MQ 引入后是不是只是把压力往后挪了

回答思路：

- 是的，从某种意义上说，MQ 就是在做“削峰填谷”，把同步写库压力转成异步排队消化。
- 但它的意义不是凭空减少总工作量，而是避免在用户请求线程里同步完成全部数据库写操作。
- 对秒杀这种强峰值业务来说，这样可以让前台更快完成受理，同时把后续处理放到可补偿、可恢复的后台链路中。

### 5.4 为什么还要做超时关单和库存回补

回答思路：

- 秒杀下单成功不代表用户一定会支付。
- 如果不做超时关闭，库存会被未支付订单长期占用，影响后续售卖。
- 所以需要在订单超时后自动取消订单、恢复库存和购买资格，并保证与支付并发时不会出现双重回补或状态错乱。

### 5.5 为什么使用延迟队列 + Spring Task 兜底

回答思路：

- 纯 `Spring Task` 扫描实现简单，但时效性依赖扫描频率，频率太低会延迟关单，频率太高又会增加无效扫描成本。
- 延迟队列能更接近订单到期时间触发，时效更好。
- 但延迟队列也不能完全替代兜底逻辑，所以我保留低频扫描用于补偿漏处理订单，兼顾时效和可靠性。

### 5.6 为什么要补布隆过滤器和缓存空值

回答思路：

- 秒杀系统之外，项目里还有普通查询接口，也会面临缓存穿透问题。
- 只用缓存空值可以挡住反复访问同一个非法 ID 的情况，但第一次非法请求仍会打到数据库。
- 布隆过滤器可以把明显不存在的数据提前拦掉，和空值缓存联合后，对恶意穿透更稳。

## 6. 最推荐的 1 分钟自述

这个项目我主要做的是一个高并发秒杀系统的架构演进。最开始我先保留了 `MySQL-only` 的同步下单方案，主要问题是高并发下数据库热点库存行竞争非常严重。第二阶段我引入了 `Redis + Lua`，把库存校验和一人一单判断前置到缓存层，大量无效请求直接在 Redis 层失败返回，数据库压力明显下降。第三阶段我继续把成功请求从同步写库改造成 `Redis 预占资格 + Kafka 异步落库`，并补齐了 pending-send 补偿、超时关单、库存回补、支付与关单并发控制，以及布隆过滤器、逻辑过期和旁路缓存一致性方案。最后我对三套架构做了压测对比，在 `5k` 级并发、库存仅 `100/500` 的高反差秒杀场景下，系统总请求量达到 `3.4w+`，最终只有 `100/500` 个请求进入成功链路，库存与订单最终严格一致。我认为这个项目的核心亮点，不只是提升了并发能力，更重要的是把秒杀成功链路做成了可恢复、可补偿、可观测的异步闭环。

## 7. 最推荐的 3 分钟深挖版

如果面试官愿意听展开版，可以按下面顺序讲：

1. 先讲业务目标：秒杀场景需要解决超卖、一人一单、数据库热点竞争和未支付订单占库存问题。
2. 再讲第一阶段：`MySQL-only`，说明为什么数据库会成为瓶颈。
3. 再讲第二阶段：`db-cache`，重点讲 `Redis + Lua` 怎样做前置过滤，以及为什么这阶段入口吞吐提升明显。
4. 再讲第三阶段：`db-cache-mq`，说明为什么仅有前置过滤还不够，成功请求仍然需要异步消化，于是引入 Kafka。
5. 接着讲状态机闭环：超时关单、库存回补、购买资格恢复、订单复用再次抢购、支付与关单并发控制。
6. 最后讲压测结论：单看当前本机单节点入口吞吐，`db-cache` 最强；但从完整工程能力和系统闭环看，`db-cache-mq` 是最成熟的终态。

## 8. 使用建议

- 简历上优先放“要点版”或“量化版”，不要整段复制展开说明。
- 面试开场优先用“1 分钟自述”，等面试官追问再切到“3 分钟深挖版”。
- 讲压测时一定区分“入口吞吐”和“最终异步落库闭环”，不要把两类指标混为一谈。
- 不要硬说 `db-cache-mq` 在所有维度都比 `db-cache` 强，这会和真实压测结果冲突。
