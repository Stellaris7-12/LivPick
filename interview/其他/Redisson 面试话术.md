# Redisson 面试话术

## 1. 先讲定位：为什么项目里要引入 Redisson

在这个项目里，我引入 Redisson 不是为了单纯替代 `StringRedisTemplate`，而是因为它把 Redis 常见的分布式能力做成了更高层的 Java 对象封装，适合直接承接业务层的并发控制和调度场景。

这个项目里，Redisson 主要用在 3 个地方：

1. 分布式锁：解决秒杀异步落库时的重复消费和并发下单问题
2. 延迟队列：解决订单超时关闭和库存回流问题
3. 布隆过滤器：解决缓存穿透问题

也就是说，Redis 在这个项目里主要承担数据和高并发入口能力，Redisson 则承担更偏“分布式协调”和“高级数据结构”的能力。

---

## 2. 项目里 Redisson 分布式锁是怎么用的

### 2.1 解决的问题

分布式锁主要解决的是：

- Kafka 消费端可能重复消费同一条消息
- 多实例部署时，同一用户的下单消息可能并发落库
- 如果不加控制，可能出现重复创建订单的问题

### 2.2 实现方式

在当前项目里，我是在秒杀异步落库时按 `userId` 维度加锁，大致思路是：

1. Kafka Consumer 收到下单消息
2. 以 `lock:order:{userId}` 为 key 获取 Redisson 的 `RLock`
3. 尝试加锁
4. 加锁成功后，再执行查重、扣减库存、创建订单
5. 最终在 `finally` 里释放锁

为什么按 `userId` 加锁，而不是按全局加锁？  
因为我只需要串行化“同一个用户”的下单落库，不需要把所有用户的请求都串起来，否则锁粒度太粗，会明显影响吞吐。

### 2.3 为什么还要数据库查重和唯一索引

Redisson 锁不是唯一兜底。  
我在这个项目里是多层保护：

1. Redis Lua 在入口做一人一单校验
2. Redisson 锁在消费端控制并发
3. 数据库再做查重
4. 数据库唯一索引 `(voucher_id, user_id)` 做最终兜底

因为分布式锁主要是降低并发冲突概率和保护临界区，最终的一致性兜底还是应该落在数据库层。

### 2.4 为什么用 Redisson，不手写 Redis 锁

如果只用 `SETNX + EXPIRE` 手写锁，要自己处理很多细节：

- 锁过期时间怎么设置
- 线程执行业务时间超过过期时间怎么办
- 删除锁时怎么避免误删别人的锁
- 可重入怎么处理
- 网络抖动和异常场景怎么处理

Redisson 已经把这些复杂度大部分封装掉了，直接给我一个 `RLock`，使用成本更低，也更适合项目里直接落地。

## 3. 项目里 Redisson 延迟队列是怎么用的

### 3.1 解决的问题

延迟队列主要解决：

- 用户下单后长时间不支付，会占用库存
- 如果不自动关单，库存无法及时释放
- 单纯依赖数据库定时扫表，实时性一般，而且随着数据量变大，扫表压力会升高

### 3.2 实现流程

这个项目里我的流程是：

1. Kafka Consumer 创建订单成功
2. 构造 `OrderTimeoutMessage`
3. 将消息放入 Redisson 延迟队列
4. 到达超时时间后，延迟队列把消息转移到阻塞队列
5. 后台线程消费这条消息
6. 执行 `closeTimeoutOrder(orderId)`
7. 如果订单当前还是“未支付”，就关闭订单
8. 关闭成功后回补数据库库存和 Redis 秒杀资格

### 3.3 为什么还要加 Spring Task 兜底

我这里没有只依赖 Redisson 延迟队列，而是又加了一层 Spring Task 定时扫描兜底。

原因是：

- 延迟队列虽然能解决大部分场景，但异步消费本身也可能异常
- 比如消费者线程挂掉、服务重启、队列消费失败，都可能导致漏关单

所以我又补了一个低频的 `@Scheduled` 定时任务：

1. 周期性扫描超时且未支付的订单
2. 再次调用统一的关单方法

这样形成“双保险”：

- Redisson 延迟队列负责主流程的实时调度
- Spring Task 负责兜底补偿

### 3.4 为什么关单要用状态条件更新

因为支付和关单可能并发发生。  
如果用户刚完成支付，延迟队列也刚好来关单，这两个操作会竞争同一条订单状态。

所以我这里采用的是基于订单状态条件更新的 CAS 思路：

- 支付只允许 `status = 1 -> 2`
- 关单只允许 `status = 1 -> 4`

谁先更新成功，谁就拿到状态变更权；另一个操作更新行数为 0，就说明状态已经被别人改过，不再继续执行。

## 4. 项目里 Redisson 布隆过滤器是怎么用的

### 4.1 解决的问题

布隆过滤器主要解决缓存穿透问题，也就是大量不存在的数据请求反复打到数据库。

这个项目里，我把它用在店铺查询场景上。

### 4.2 实现流程

流程是：

1. 应用启动时初始化 `RBloomFilter`
2. 从数据库加载已有店铺 ID
3. 用户查询店铺时，先查布隆过滤器
4. 如果布隆过滤器判断“不存在”，直接返回，不访问 Redis 和数据库
5. 如果布隆过滤器判断“可能存在”，再走缓存查询
6. Redis 未命中后再查数据库
7. 如果数据库也没有，再写空值缓存

### 4.3 为什么要“布隆过滤器 + 缓存空值”组合

因为它们各自解决的问题不同：

- 布隆过滤器负责拦住绝大多数明显不存在的数据请求
- 缓存空值负责兜住少量误判请求和第一次穿透请求

如果只用布隆过滤器，少量误判仍然会打到数据库；  
如果只用缓存空值，第一次无效请求还是会打库。  
所以组合起来效果更完整。

### 4.4 为什么用 Redisson 的布隆过滤器

因为 Redisson 已经把布隆过滤器封装成 `RBloomFilter`：

- 初始化方便
- 查询方便
- 直接依赖 Redis 存储位图和元数据
- 不需要自己手写哈希和位运算逻辑

对于业务项目来说，可维护性更好。

## 5. 为什么这个项目要用 Redisson

如果面试官直接问“为什么选 Redisson”，我会从 4 个角度回答：

### 5.1 API 更高层

Redisson 把 Redis 常见分布式能力封装成了 Java 对象，比如：

- `RLock`
- `RDelayedQueue`
- `RBloomFilter`
- `RMap`
- `RAtomicLong`

业务层直接调用，开发成本更低。

### 5.2 降低手写 Redis 方案的复杂度

很多能力如果自己用原生 Redis 命令拼，会涉及大量边界处理，比如锁续期、误删锁、延迟调度、布隆过滤器位图管理等。Redisson 帮我把这些复杂度封装掉了。

### 5.3 更适合承接业务层并发控制

像秒杀消费端锁、延迟关单、布隆过滤器这种能力，本质上已经不是简单的缓存读写，而是更偏业务协调和并发控制，这正是 Redisson 的优势场景。

### 5.4 与当前项目技术栈匹配

这个项目本身已经高度依赖 Redis，所以继续用 Redisson 扩展 Redis 能力，比单独再引入一套完全不同的中间件成本更低。

## 6. Redisson 分布式锁的底层原理怎么简单讲

如果面试官问底层原理，我一般不会一下讲太深，而是讲够用的版本。

### 6.1 加锁原理

Redisson 分布式锁底层本质上还是基于 Redis：

- 尝试用原子命令占有一个锁 key
- 如果成功，就认为当前线程拿到了锁
- 锁 value 里会带线程标识，避免误删

### 6.2 可重入

Redisson 支持可重入锁。  
同一个线程再次获取同一把锁时，不是简单失败，而是会增加重入计数。

### 6.3 自动续期

这是 Redisson 很关键的一点。  
如果业务执行时间超过了初始锁超时时间，Redisson 的 watchdog 机制会自动给锁续期，避免“业务还没执行完，锁先过期被别人拿走”的问题。

### 6.4 解锁

解锁时不是直接 `DEL key`，而是会校验当前线程是不是锁持有者，防止误删别人的锁。

### 6.5 一句话总结

简单说，Redisson 锁本质上还是 Redis 锁，只不过它把可重入、续期、线程标识校验这些关键细节都封装好了。

## 7. Redisson 延迟队列的底层原理怎么简单讲

Redisson 延迟队列底层不是 Kafka 那种真正的 Broker 延迟消息，而是基于 Redis 的组合数据结构实现的。

可以这样理解：

1. 延迟消息先按到期时间存起来
2. 到期后再转移到阻塞队列
3. 消费线程从阻塞队列里取消息处理

所以它更适合：

- 中小型业务场景
- 已经依赖 Redis 的项目
- 对接入成本敏感的系统

但如果消息量特别大、调度要求特别复杂，专业 MQ 的延迟消息能力会更合适。

---

## 8. Redisson 布隆过滤器的底层原理怎么简单讲

布隆过滤器底层本质上是：

- 一个很长的位数组
- 多个哈希函数

写入一个元素时：

- 对元素做多次哈希
- 把对应位置的 bit 设成 1

查询一个元素时：

- 也做同样的多次哈希
- 如果有任意一个位置是 0，就说明这个元素一定不存在
- 如果所有位置都是 1，只能说明它“可能存在”

所以布隆过滤器的特点是：

- 不存在的数据一定能判断出来
- 存在的数据可能会被误判为存在

这就是它“有误判、无漏判”的核心特性。

## 9. 常见 Redisson 基础知识

### 9.1 Redisson 是什么

Redisson 是一个基于 Redis 的 Java 客户端框架，除了普通读写外，还提供了很多分布式对象和分布式工具。

### 9.2 Redisson 和 StringRedisTemplate 的区别

`StringRedisTemplate` 更偏底层，适合直接操作 Redis 命令。  
Redisson 更偏对象化和分布式能力封装，适合锁、队列、布隆过滤器、分布式集合等场景。

### 9.3 Redisson 常见能力

- 分布式锁 `RLock`
- 读写锁 `RReadWriteLock`
- 信号量 `RSemaphore`
- 延迟队列 `RDelayedQueue`
- 阻塞队列 `RBlockingQueue`
- 布隆过滤器 `RBloomFilter`
- 原子类 `RAtomicLong`
- 分布式集合 / Map / Set / List

### 9.4 Redisson 适合什么场景

- 秒杀、抢购等并发控制
- 分布式任务协调
- 延迟任务
- 缓存穿透防护
- 分布式计数器和限流辅助

## 10. Redisson 常见面试提问

### 10.1 为什么不用数据库锁，非要用 Redisson 锁

因为数据库锁更适合保护数据库事务内的资源，但秒杀这类高并发场景如果大量请求都直接落数据库，热点行竞争会非常严重。  
Redisson 锁可以把部分并发控制前移到 Redis 层，减轻数据库压力。

### 10.2 Redisson 锁一定可靠吗

可靠性比手写 Redis 锁高很多，但它不是“绝对无问题”。  
比如 Redis 本身宕机、网络分区、主从切换等都可能影响锁语义，所以最终业务关键约束仍然要由数据库兜底。

### 10.3 Redisson 锁和唯一索引是什么关系

不是二选一，而是不同层级的保护：

- Redisson 锁负责降低并发冲突
- 唯一索引负责最终一致性兜底

### 10.4 Redisson 延迟队列和 MQ 延迟消息怎么选

如果项目已经依赖 Redis、消息量不大、接入成本优先，我更倾向 Redisson 延迟队列。  
如果消息量大、可靠性和调度能力要求高，我会更倾向专业 MQ 的延迟消息能力。

### 10.5 布隆过滤器会不会误杀正常请求

标准布隆过滤器不会把存在的数据判断成不存在，也就是不会“漏判”；  
它的问题是可能把不存在的数据判断成存在，也就是“误判”。  
所以它不会误杀正常请求，但会放过少量本应拦截的无效请求。

### 10.6 Redisson 为什么适合这个项目

因为这个项目本身已经大量依赖 Redis，而秒杀、超时关单、缓存穿透这些问题本质上都和分布式协调、高级数据结构有关，用 Redisson 可以把 Redis 的能力更自然地接到业务里。

## 11. 项目里的完整回答模板

如果面试官让我整体讲一遍 Redisson 在项目里的作用，我会这样回答：

“这个项目里我主要把 Redisson 用在了三个地方。第一是分布式锁，在 Kafka 异步落库时按用户维度加锁，防止重复消费或并发落库导致重复下单；第二是延迟队列，订单创建成功后投递超时消息，到期后自动关单并回补库存，同时我又加了 Spring Task 做兜底扫描，避免异步链路异常导致漏关单；第三是布隆过滤器，在店铺查询入口先判断 ID 是否可能存在，再结合缓存空值一起解决缓存穿透。

之所以选 Redisson，是因为它把 Redis 的分布式能力做成了更高层的 Java 封装，比如 `RLock`、`RDelayedQueue`、`RBloomFilter`，比我自己用原生命令拼装更稳、更省开发成本。底层上，Redisson 锁本质还是 Redis 锁，只是它帮我封装了可重入、自动续期和持有者校验这些关键细节，所以特别适合在这个高并发项目里直接落地。”
