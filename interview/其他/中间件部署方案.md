# 中间件部署方案

## 1. 最终统一口径

这个项目的中间件部署口径统一为：

- 开发联调阶段：本地部署
- 第一轮功能压测：本地可先做
- 更真实的并发压测 / 生产口径：迁移到云上或云上集群

当前涉及的中间件主要是：

- Kafka
- Redis

一句话总结：

**开发时本地单机，压测和生产时按中间件特点分别上云扩展。**

---

## 2. Kafka 部署方案

## 2.1 开发环境

当前项目开发联调阶段，Kafka 推荐采用：

- Kafka `4.1.x`
- KRaft 模式
- 单 Broker
- `broker,controller` combined mode
- 不使用 ZooKeeper

这样选的原因：

- 当前目标是跑通秒杀异步落库和缓存删除补偿重试
- 单节点最容易调试 Producer、Consumer、Topic 和日志
- Kafka 官方明确 combined mode 更适合开发环境和小型场景
- Kafka 4.x 口径已经转向 KRaft，不再建议新部署继续用 ZooKeeper

### 开发环境推荐配置思路

```properties
process.roles=broker,controller
node.id=1

listeners=PLAINTEXT://localhost:9092,CONTROLLER://localhost:9093
advertised.listeners=PLAINTEXT://localhost:9092
listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
controller.listener.names=CONTROLLER
controller.quorum.bootstrap.servers=localhost:9093

log.dirs=D:/kafka/kraft-combined-logs
num.partitions=1
offsets.topic.replication.factor=1
transaction.state.log.replication.factor=1
transaction.state.log.min.isr=1
min.insync.replicas=1
auto.create.topics.enable=false
```

当前项目至少需要两个 Topic：

- `seckill-order-create`
- `cache-shop-delete-retry`

开发环境建议：

- 分区数：1
- 副本数：1

### 当前项目 Spring Kafka 配置怎么讲

当前项目应用侧 Kafka 配置主线是：

```yaml
spring:
  kafka:
    bootstrap-servers: ${KAFKA_BOOTSTRAP_SERVERS:localhost:9092}
    producer:
      acks: all
      retries: 3
    consumer:
      group-id: ${KAFKA_CONSUMER_GROUP:livpick-consumer-group}
      auto-offset-reset: latest
```

后续如果要继续强化可靠性，可以补：

- `enable.idempotence=true`
- `max.in.flight.requests.per.connection=1`
- `listener.ack-mode=record`
- `listener.concurrency`

---

## 2.2 压测阶段

Kafka 的压测口径建议分两层讲：

### 第一层：功能性压测

本地环境可以先做，主要验证：

- 下单消息是否正常发送
- Consumer 是否正常落库
- 缓存补偿消息是否会触发

### 第二层：更真实的性能压测

如果后续要更真实地观察：

- Broker 吞吐
- 多消费者并发
- 分区扩展能力
- 网络延迟和副本行为

那就建议迁移到云上 Kafka 再做压测。

这时候推荐：

- 云上托管 Kafka 服务
或者
- 云上 KRaft 集群

---

## 2.3 生产环境

生产口径下，Kafka 推荐采用：

- KRaft 集群
- `3 Controller + 3 Broker`
- Broker 与 Controller 分离部署

Topic 建议：

- 分区数：3 起步
- 副本数：3
- `min.insync.replicas=2`

应用侧建议：

- `acks=all`
- `retries` 适当调大
- `enable.idempotence=true`
- Consumer 并发与分区数匹配

### 是否需要云服务

如果面试官问生产是否上云，可以统一答：

- 当前开发阶段本地部署
- 如果进入压测和生产，我会优先考虑云上托管 Kafka
- 可选服务包括：
  - 阿里云消息队列 Kafka 版
  - 腾讯云 CKafka
  - AWS MSK

### 为什么不用 ZooKeeper

统一回答：

- Kafka 官方已将 ZooKeeper 模式弃用
- 新部署应优先采用 KRaft

---

## 3. Redis 部署方案

## 3.1 开发环境

当前项目开发联调阶段，Redis 推荐采用：

- 单机 Redis
- 单实例
- 开启持久化

当前项目里 Redis 主要承担：

- Lua 原子校验
- 秒杀库存和用户资格
- 登录态
- 缓存
- Redisson 分布式锁
- Redisson 延迟队列
- Redisson Bloom Filter

所以开发环境单机 Redis 已经足够：

- 结构简单
- 调试方便
- 可以直接验证 Lua、锁、延迟队列和布隆过滤器链路

### 开发环境建议配置思路

建议至少开启：

- `appendonly yes`
- 合理的 `maxmemory`
- 合理的淘汰策略，例如 `allkeys-lru` 或按业务再调

如果是本地 Windows 或 Docker 环境，重点是保证：

- Redis 能稳定启动
- 项目和 Redisson 都能连接
- 持久化打开，避免调试中频繁丢数据

---

## 3.2 为什么开发环境不直接用 Redis Cluster

当前项目不建议开发阶段直接上 Redis Cluster，原因有三点：

### 1. 业务还不需要

当前阶段重点是跑通功能，不是做 Redis 横向扩容。

### 2. 当前 Lua 脚本链路更适合单机或非分片架构

当前秒杀链路里有 Lua 原子校验，而且同时操作多个 key，例如：

- `seckill:stock:{voucherId}`
- `seckill:order:{voucherId}`

如果直接上 Redis Cluster，就要额外考虑：

- 多 key 是否落在同一 slot
- key 是否需要 hash tag
- Lua 脚本在集群模式下的 key 路由约束

这会明显增加复杂度。

### 3. Redisson 的锁、延迟队列、布隆过滤器都更适合先在简单拓扑上验证

开发阶段先在单机 Redis 或主从环境把这些能力跑通，比一开始就堆集群更合理。

---

## 3.3 压测阶段

Redis 的压测也建议分两层讲：

### 第一层：本地功能压测

本地可以先验证：

- Lua 校验性能
- 缓存命中链路
- Redisson 锁和延迟队列是否正常工作

### 第二层：更真实的性能压测

如果后续要更真实地看：

- Redis QPS
- 热点 key 压力
- 主从同步
- failover 行为

建议迁移到云上 Redis 或更接近生产的主从环境。

---

## 3.4 生产环境怎么选：Sentinel 还是 Cluster

对于这个项目，我建议先按两档口径来讲。

### 第一档：当前项目生产第一阶段

优先采用：

- Redis 主从复制
- Redis Sentinel

原因：

- 当前项目 Redis 主要用于缓存、高并发资格校验、锁、延迟队列、布隆过滤器
- 业务模型更偏单体、热点访问和高频读写
- 先做高可用比先做分片更重要

Redis 官方文档也说明：

- Sentinel 适合非 Cluster 模式下的高可用
- 典型做法是主从 + 至少 3 个 Sentinel

### 第二档：如果后续数据量和吞吐继续扩大

再考虑：

- Redis Cluster

适用场景：

- 数据容量继续上升
- 单节点内存瓶颈明显
- QPS 已经超出单主实例承载能力

但是对当前这个项目，不建议一上来就把“生产环境默认 Redis Cluster”说死。  
更稳妥的回答是：

**先主从 + Sentinel 保高可用，后续容量和吞吐上来再演进到 Cluster。**

---

## 3.5 生产环境 Redis 推荐架构

当前项目生产阶段推荐先采用：

- 1 主
- 2 从
- 3 Sentinel

这样可以兼顾：

- 主从复制
- 自动故障转移
- 客户端主节点发现

如果上云，对应口径可以说：

- 当前开发本地单机 Redis
- 如果进入压测或生产，我会优先考虑云上 Redis 主从版或高可用版

中国区可选口径：

- 阿里云 Redis
- 腾讯云 Redis

---

## 4. 当前项目最终推荐方案

## 4.1 开发联调阶段

- Kafka：本地单机，Kafka 4.1.x，KRaft，单 Broker，combined mode
- Redis：本地单机 Redis

这样最适合当前阶段把：

- Kafka 异步下单
- Kafka 补偿重试
- Redis Lua
- Redisson 锁
- Redisson 延迟队列
- Redisson Bloom Filter

这些链路全部跑通。

## 4.2 后续压测阶段

- Kafka：优先迁移云上 Kafka 或云上 KRaft 集群
- Redis：优先迁移云上高可用 Redis

这样更适合观察真实吞吐、网络和集群行为。

## 4.3 生产口径

- Kafka：KRaft 集群，`3 Controller + 3 Broker`
- Redis：先主从 + Sentinel，高可用优先；后续容量和吞吐继续增大时再考虑 Cluster

---

## 5. 面试时建议的统一表达

你可以直接这样说：

“这个项目在开发联调阶段，我采用的是本地部署中间件。Kafka 用的是 4.1.x 的 KRaft 单 Broker combined mode，不再依赖 ZooKeeper；Redis 用的是单机实例，先把 Lua 校验、缓存、Redisson 锁、延迟队列和布隆过滤器这些功能链路跑通。

如果后续进入压测阶段，我会继续分两步走：第一轮功能压测可以先在本地做；如果要更真实地验证吞吐、网络和并发行为，就迁移到云上环境。Kafka 这边我会优先考虑云上托管 Kafka 或 KRaft 集群，Redis 这边我会优先采用云上高可用 Redis。

如果按生产口径设计，Kafka 我会采用 KRaft 集群，推荐 3 Controller + 3 Broker；Redis 我会先采用主从复制加 Sentinel，优先解决高可用问题，后续容量和吞吐继续上来，再演进到 Redis Cluster。”
