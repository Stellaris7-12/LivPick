# 布隆过滤器实现链路与面试讲解

## 1. 先说结论

这个项目里的布隆过滤器不是 RedisBloom 模块实现的，而是 **Redisson `RBloomFilter`** 在普通 Redis 之上做的一层封装。

它的核心作用是：

1. 在店铺详情查询入口先做一次“是否可能存在”的快速判断
2. 提前拦截明显不存在的 `shopId`
3. 减少缓存穿透导致的无效 Redis / MySQL 查询

这个能力主要服务于：

- `GET /shop/{id}` 店铺详情查询

如果面试官只问一句“你项目里的布隆过滤器是干什么的”，你可以先直接回答：

> 我在店铺详情查询入口接了一个 Redisson 布隆过滤器，先判断店铺 ID 是否可能存在。不存在就直接返回，存在再继续走缓存空值和数据库查询，这样可以降低缓存穿透对 Redis 和 MySQL 的冲击。

从调用顺序看，完整链路是：

1. Spring Boot 启动
2. `ShopBloomFilterService.init()` 初始化布隆过滤器
3. 如果过滤器为空，则执行 `rebuild()`
4. 用户请求 `GET /shop/{id}`
5. `ShopServiceImpl.queryById()` 调 `CacheClient.queryWithBloomPassThrough(...)`
6. `queryWithBloomPassThrough(...)` 先执行 `shopBloomFilterService.mightContain(id)`
7. 如果布隆过滤器判断“不可能存在”，直接返回 `null`
8. 如果判断“可能存在”，再继续走缓存空值和数据库查询

## 3. 具体类与方法

## 3.1 配置类：`LivPickProperties.Bloom`

配置在 [LivPickProperties](C:/Users/heyunhui/IdeaProjects/LivPick/src/main/java/com/livepick/config/LivPickProperties.java)：

```java
public static class Bloom {
    private String shopFilterName = "bf:shop:id";
    private long expectedInsertions = 100_000L;
    private double falseProbability = 0.03D;
}
```

这 3 个参数分别表示：

- `shopFilterName`
  - Redis 里布隆过滤器的名字
  - 当前值是 `bf:shop:id`

- `expectedInsertions`
  - 预估要插入多少个元素
  - Redisson 会用它计算位图大小

- `falseProbability`
  - 允许的误判率
  - 当前配置是 `3%`

面试时可以这样解释：

> 布隆过滤器不是随便开一个 bitset 就行，它需要先根据预估数据量和可接受误判率去计算位图大小和哈希次数。我的项目把这两个参数抽成了配置项，初始化时交给 Redisson 去计算。

## 3.2 布隆过滤器服务：`ShopBloomFilterService`

这个类是整个链路的核心。

### `init()`

```java
@PostConstruct
public void init() {
    shopBloomFilter = redissonClient.getBloomFilter(livPickProperties.getBloom().getShopFilterName());
    shopBloomFilter.tryInit(
            livPickProperties.getBloom().getExpectedInsertions(),
            livPickProperties.getBloom().getFalseProbability()
    );
    if (shopBloomFilter.count() == 0) {
        rebuild();
    }
}
```

作用：

1. Spring 启动后自动执行
2. 根据配置名拿到 `RBloomFilter`
3. 调 `tryInit(...)` 初始化参数
4. 如果当前过滤器看起来是空的，就执行一次全量重建

需要注意：

- `init()` 每次启动都会执行
- 但 `rebuild()` **不会**每次启动都执行
- 只有 `count() == 0` 时才会重建

这点面试里很重要，因为它说明：

- 当前项目有“启动时自动初始化”
- 但没有“每次启动全量刷新”

### `mightContain(Long shopId)`

```java
public boolean mightContain(Long shopId) {
    return shopBloomFilter.contains(String.valueOf(shopId));
}
```

作用：

- 对外暴露“是否可能存在”的判断能力
- 这是查询链路真正使用的方法

面试时要强调：

- 布隆过滤器只能回答“可能存在 / 一定不存在”
- 它**不能**回答“确定存在”

### `addShop(Long shopId)`

```java
public void addShop(Long shopId) {
    shopBloomFilter.add(String.valueOf(shopId));
}
```

作用：

- 给单个店铺做增量加入

但当前现状是：

- 这个方法已经写了
- **目前没有任何地方调用**

所以它现在只是“预留能力”，不是实际生效的维护逻辑。

### `rebuild()`

```java
public void rebuild() {
    shopBloomFilter.delete();
    shopBloomFilter = redissonClient.getBloomFilter(livPickProperties.getBloom().getShopFilterName());
    shopBloomFilter.tryInit(...);
    List<Shop> shops = shopMapper.selectList(null);
    shops.forEach(shop -> shopBloomFilter.add(String.valueOf(shop.getId())));
}
```

作用：

1. 删除当前过滤器
2. 重新初始化
3. 全表扫描 `tb_shop`
4. 把所有 `shopId` 重新塞进布隆过滤器

这是当前项目里唯一真正意义上的“全量维护”逻辑。

## 3.3 查询接入点：`ShopServiceImpl.queryById()`

入口代码在 [ShopServiceImpl](C:/Users/heyunhui/IdeaProjects/LivPick/src/main/java/com/livepick/service/impl/ShopServiceImpl.java)：

```java
Shop shop = cacheClient.queryWithBloomPassThrough(
        CACHE_SHOP_KEY,
        id,
        shopBloomFilterService::mightContain,
        Shop.class,
        this::getById,
        CACHE_SHOP_TTL,
        TimeUnit.MINUTES
);
```

这里的职责划分是：

- `ShopServiceImpl`
  - 负责把“店铺查询业务”接到缓存组件上

- `CacheClient.queryWithBloomPassThrough(...)`
  - 负责把“布隆过滤器预判 + 缓存空值 + DB 回源”整合到一个模板方法里

- `shopBloomFilterService::mightContain`
  - 是传进去的布隆过滤器判断函数

面试时可以这样讲：

> 我没有把布隆过滤器判断散落在业务代码里，而是把它封装到 `CacheClient` 的查询模板方法中。这样店铺详情查询只要接一个 `Predicate` 就能复用“布隆过滤器预判 + 缓存空值”的统一逻辑。

## 3.4 缓存模板方法：`CacheClient.queryWithBloomPassThrough(...)`

逻辑非常简单：

```java
if (!bloomFilterPredicate.test(id)) {
    return null;
}
return queryWithPassThrough(...);
```

也就是说：

1. 先过布隆过滤器
2. 如果判断不可能存在，直接返回
3. 如果可能存在，再走缓存空值穿透保护和数据库回源

这一层的价值在于：

- 布隆过滤器拦截的是“明显不存在”
- 缓存空值兜住的是“布隆过滤器误判成可能存在，但 DB 实际不存在”

所以两者不是冲突关系，而是组合关系。

## 4. 底层原理：它为什么能拦截缓存穿透

布隆过滤器本质上是：

- 一个很大的 bitmap
- 多个哈希函数

插入一个 `shopId` 时：

1. 对这个 `shopId` 做多次 hash
2. 得到多个下标
3. 把 bitmap 里这些 bit 位都置成 `1`

判断一个 `shopId` 是否存在时：

1. 对这个 `shopId` 做同样的多次 hash
2. 查对应的多个 bit 位
3. 只要有一个 bit 是 `0`，就能确定这个元素**一定不存在**
4. 如果所有 bit 都是 `1`，只能说明它**可能存在**

所以它的特点是：

- 不会漏判已有数据
- 会有误判
- 特别适合做“快速排除”

这就是它能防缓存穿透的原因：

- 随机传一个根本不存在的 `shopId`
- 很大概率在布隆过滤器这层就被挡掉
- 不会继续打 Redis 缓存空值和 MySQL

## 5. Redis 里到底长什么样

当前项目用的是 Redisson `RBloomFilter`，不是 RedisBloom 模块。

所以你会看到两个 key：

1. `bf:shop:id`
2. `{bf:shop:id}:config`

### 5.1 `bf:shop:id`

这是布隆过滤器的**位图本体**。

Redis 里 bitmap 底层就是 `string`，所以：

```redis
TYPE bf:shop:id
```

返回 `string` 是正常的。

### 5.2 `{bf:shop:id}:config`

这是布隆过滤器的**配置元数据**。

里面一般会存：

- `size`
- `hashIterations`
- `expectedInsertions`
- `falseProbability`

可以这样看：

```redis
HGETALL {bf:shop:id}:config
```

### 5.3 为什么 `BF.INFO` 不可用

因为：

- `BF.INFO` 是 RedisBloom 模块命令
- 你当前项目没有用 RedisBloom
- 当前项目用的是 Redisson 自己在普通 Redis 上封装的布隆过滤器

所以这条命令报错是正常的：

```redis
BF.INFO bf:shop:id
```

## 6. 当前实现的维护现状

这部分是面试里最容易加分的地方，因为它体现你不是只会说“我用了布隆过滤器”，而是知道它的运维成本。

## 6.1 已有的维护逻辑

当前代码里有：

1. 启动时初始化 `init()`
2. 启动时如果过滤器为空就 `rebuild()`
3. 一个预留的 `addShop(shopId)` 增量加入方法

## 6.2 当前缺失的维护逻辑

当前**没有**：

1. 新增店铺后的自动 `addShop(id)`
2. 删除店铺后的重建或同步清理
3. 定时重建任务
4. 手动触发重建接口

也就是说，现在的布隆过滤器更像一个：

- 启动时自动装载一次的“静态快照”

而不是一个：

- 持续实时维护的数据结构

## 6.3 这会带来什么问题

如果后续新增了店铺，但应用没有触发 `rebuild()`，就可能出现：

1. 数据库里有这家店
2. 缓存里也可能没有问题
3. 但布隆过滤器没收录这个 `shopId`
4. `mightContain(id)` 直接返回 `false`
5. 请求在最前面就被错误拦截

严格说这不是“布隆过滤器误判率”问题，而是：

- **过滤器数据没有及时维护**

面试时可以主动提这点：

> 当前项目已经把布隆过滤器接入了查询链路，但维护还不算完整。现在只有启动时空过滤器自动重建，没有定时重建和新增店铺后的增量维护。这个我会在后续迭代里补上，否则业务数据变化后过滤器可能会陈旧。

## 7. 面试时怎么讲“为什么不用缓存空值就够了”

这是很典型的问题。

可以这样回答：

> 缓存空值可以解决“反复查不存在数据”的问题，但第一次请求还是会打到数据库。如果攻击者不断构造大量随机不存在的店铺 ID，请求会一直穿过缓存层去打 DB。  
> 布隆过滤器的价值就是把这类明显不存在的 ID 在更前面挡住，减少第一次无效请求打到 DB 的机会。  
> 所以这两个方案不是二选一，而是组合使用：布隆过滤器负责快速排除，缓存空值负责兜住误判和少量漏网请求。

---

## 8. 面试时怎么讲“为什么不用 RedisBloom 模块”

可以这样回答：

> 当前项目选的是 Redisson `RBloomFilter`，主要是因为项目本身已经在用 Redisson 做分布式锁和延迟队列，这样布隆过滤器也能统一走同一套客户端，不需要额外要求 Redis 服务器安装 RedisBloom 模块。  
> 这种方式部署门槛更低，适合本地联调和中小项目演示。  
> 但代价是可观测性不如 RedisBloom 直接，比如不能直接用 `BF.INFO` 这种命令查看状态。
