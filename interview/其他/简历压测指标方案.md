# 简历压测指标方案

这份文档的目标不是先“写一个好看的数字”，而是先把最值得测、最适合写进简历的指标固定下来。后续拿到真实压测结果后，直接替换文中的 `[待实测]` 即可。

## 1. 最值得写进简历的指标

### 1.1 秒杀主链路吞吐与延迟

这是最能体现项目价值的一组指标，优先级最高。

- 吞吐量：`TPS / QPS`
- 响应时间：平均 RT、`P95`、`P99`
- 错误率：超时、5xx、业务失败占比
- 秒杀成功率：成功下单数 / 合法请求数
- Kafka 消费堆积：`consumer lag`
- 数据库写入压力：订单写入 TPS、库存更新 TPS
- 最终一致性结果：超卖数、重复下单数、库存不一致数

建议对比两组方案：

- 基线方案：同步写库下单
- 当前方案：`Redis + Lua + Kafka` 异步削峰

简历结果模板：

- 将秒杀下单链路从同步写库改造为 `Redis + Lua + Kafka` 异步方案，压测下 TPS 提升至 `[待实测]`，较基线提升 `[待实测]`，接口 `P95` 从 `[待实测]` 降至 `[待实测]`。

## 2. 缓存穿透治理指标

这部分不要主打极限吞吐，而是主打“无效流量治理效果”。

### 2.1 测试场景

- 构造大量不存在的 `shopId`
- 对比三种方案：
  - 无防护
  - 仅缓存空值
  - 布隆过滤器 + 缓存空值

### 2.2 关注指标

- 数据库查询次数
- Redis 查询次数
- 无效请求平均 RT / `P95`
- 布隆过滤器阶段拦截率
- 空值缓存命中率
- 布隆过滤器误判率

简历结果模板：

- 引入布隆过滤器 + 缓存空值双层防护，在高并发无效 `shopId` 请求场景下，将数据库无效查询量降低 `[待实测]`，无效请求拦截率达到 `[待实测]`。

## 3. 热点 Key 稳定性指标

这部分更适合写“稳定性提升”，不一定强调绝对吞吐。

### 3.1 测试场景

- 固定存在的热点 `shopId`
- 持续高并发查询店铺详情
- 观察缓存重建期间是否出现 RT 毛刺

### 3.2 关注指标

- 平均 RT、`P95`、`P99`
- Redis 命中率
- DB 回源次数
- 缓存重建期间的请求抖动
- 是否出现线程堆积

简历结果模板：

- 通过逻辑过期控制热点 Key 重建，将高并发热点查询场景下的数据库回源次数控制在 `[待实测]`，并将查询链路 `P95` 稳定在 `[待实测]` 以内。

## 4. 并发正确性指标

这部分比性能更重要，适合写“压测中错误数为 0”。

### 4.1 秒杀一致性

- 超卖数
- 重复下单数
- Redis 与 MySQL 最终库存不一致数

### 4.2 支付与关单竞争

- `UNPAID -> PAID` 成功率
- `UNPAID -> CANCELLED` 成功率
- 已支付订单被误关单次数
- 关单后库存回补错误次数

简历结果模板：

- 基于 Redis 资格预扣、Consumer 侧分布式锁与数据库唯一约束三层兜底，压测中超卖数、重复下单数、库存不一致数均为 `0`。
- 通过订单状态条件更新控制支付与关单竞争，压测中已支付订单误关单次数为 `0`。

## 5. 推荐的压测场景顺序

建议按下面顺序补真实数据，性价比最高：

1. 秒杀主链路吞吐与延迟
2. 秒杀库存与一人一单正确性
3. 无效 `shopId` 冲击下的缓存穿透防护
4. 热点店铺详情查询稳定性
5. 支付与超时关单竞争

## 6. 不建议现在直接写进简历的内容

下面这几类表述先不要写成“结果”：

- “理论可支持 xx TPS”
- “预估提升 xx%”
- “大概能降低 xx ms”
- “应该能把数据库压力降很多”

如果时间紧张，可以先在简历里保留“结果位置”，但不要把目标值写成已经测出来的真实结果。

## 7. 简历最终写法建议

等真实结果出来后，优先写下面三类：

1. 秒杀主链路的吞吐与延迟收益
2. 布隆过滤器 + 缓存空值带来的数据库无效查询下降
3. 超卖、重复下单、状态错乱为 `0` 的正确性结果

不建议把所有中间件都平铺直叙罗列。简历里最有区分度的，不是“用了 Redis/Kafka”，而是你把它们放在什么链路里，解决了什么高并发问题，以及压测结果如何。
