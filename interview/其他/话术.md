## 一、先讲整体：高并发系统的设计思路

开始具体讲之前先阐述一下业务背景或者场景需求：
针对本地生活优惠券秒杀场景，目前的痛点是活动开始瞬间流量集中、库存热点竞争严重、用户重复下单风险高，对系统吞吐和可用性要求高，对个别非核心查询的强一致性要求不高，总体架构采用“Redis前置拦截 + 消息队列削峰异步落库 + MySQL最终落地”的分层设计

我们要设计一个高并发秒杀系统，主要考虑逐层过滤的方案，前端限流（抗流量）+CDN缓存+Redis缓存（抗读写）+消息队列削峰+数据库兜底和最终落地
同时通过集群、数据持久化、降级等方案保证高可用，通过旁路缓存、数据库唯一索引、消息补偿重试等方案保证数据一致性

真正的高并发系统设计，不是上来就说“我用了 Redis、Kafka、Redisson”，而是先看系统在不同层会遇到什么问题，然后**分层治理**。

我现在比较认可的整体思路，是按四层来理解。

### 1. 接入层

这一层的核心目标是：**先保护系统，不要让所有流量都无脑打进业务逻辑。**

如果再往工程化继续做，我会把接入层能力补成：

- 网关层限流
- 黑白名单
- 熔断和降级
- 静态资源前移，比如 CDN

当前这个项目里，我没有完整实现网关限流和熔断，但已经在业务入口做了 benchmark-only 的控制和前置校验。  
如果以后往生产级演进，接入层应该是第一道保护。

### 2. 业务层

这一层的核心目标是：**保证业务语义正确。**

比如秒杀最核心的业务语义就是：

- 不能超卖
- 一人一单
- 重复请求不能生成重复结果
- 支付和关单并发时状态不能乱

这层常见手段包括：

- 乐观锁，比如条件更新 `stock > 0`
- 悲观锁，比如 `for update`
- 状态机
- 幂等性控制
- 唯一索引
- 分布式锁

我这个项目里，业务层主要落了这些能力：

- 秒杀库存扣减用条件更新防超卖
- 订单表 `(voucher_id,user_id)` 唯一索引兜底一人一单
- Kafka 消费端用 `Redisson RLock` 按用户加锁
- 支付和关单并发用基于订单状态的 CAS 更新
- 订单状态机支持 `UNPAID -> PAID / CANCELLED`

### 3. 中间件层

这一层的核心目标是：**削峰、缓冲、异步解耦，同时把异常链路补齐。**

这里最典型的手段就是 MQ。

MQ 不是为了“让数据库消失”，而是为了：

- 把成功请求从同步写库改造成异步消化
- 让前台线程尽快返回
- 给系统提供补偿、重试和恢复空间

但引入 MQ 后不能只讲“用了 Kafka”，还要回答 3 个问题：

1. 消息丢了怎么办
2. 重复消费怎么办
3. 消息积压怎么办

当前项目里这三点分别对应：

- 消息丢失风险
  - Producer 发送确认
  - Redis pending-send 补偿登记
- 重复消费
  - Consumer 用户锁
  - 数据库唯一索引
  - 订单状态机分支判断
- 消息积压
  - 当前还没有做真正的多 partition 扩容
  - 目前更多是可观测和可补偿
  - 如果继续演进，我会优先增加 partition 和 consumer 并发

### 4. 存储层

这一层的核心目标是：**让数据最终能落住，而且容量和性能能继续扩。**

当前项目里我已经落地的存储层能力有：

- MySQL 作为最终订单和库存状态落地
- Redis 作为缓存、资格预占和中间状态存储
- `RedisIdWorker` 生成全局唯一订单 ID

如果继续往更大规模演进，存储层的方向会是：

- 分库分表
- 雪花算法或统一 ID 服务
- 热点表拆分
- 冷热数据分层

所以如果面试官问我“高并发系统整体怎么设计”，我现在会总结成一句话：

**接入层先保护系统，业务层保证语义正确，中间件层做削峰和补偿，存储层保证最终落地和后续扩展。**

## 三、简历每一项描述怎么讲

## 1. 秒杀防超卖和一人一单

### 痛点

最开始如果只用 MySQL 做秒杀，下单链路会遇到两个典型问题：

- 高并发下库存热点行竞争严重
- 同一个用户可能在并发下重复下单

### 可能方案

这里我考虑过几种方案：

1. 只用 MySQL 乐观锁
- 库存扣减时加 `stock > 0`
- 可以解决超卖
- 但不能单独解决一人一单

2. MySQL 悲观锁
- 比如 `for update`
- 一致性更强
- 但并发性能更差

3. 业务层加分布式锁
- 能控制并发
- 但如果所有请求都先打到数据库，压力还是很大

### 最终选择

我最终选择的是：

- `Redis + Lua` 前置做资格原子校验
- 数据库唯一索引兜底
- Kafka Consumer 侧再加 `Redisson` 用户锁

### 为什么这样选

原因是我不想把超卖和一人一单都压在数据库上解决。  
数据库当然能做，但那样所有请求都会直打 MySQL，失败请求也要参与热点竞争。

而 `Redis + Lua` 的优势是：

- 先在内存里判断库存够不够
- 再判断这个用户是不是已经占用了资格
- 成功后直接在 Redis 里预扣库存、占用资格

这样绝大多数失败请求会在 Redis 层结束，不会继续冲击数据库。

同时我不是只靠 Lua 一层，而是做了三层保护：

1. Redis + Lua 前置原子校验
2. Consumer 侧 `Redisson RLock`
3. 数据库唯一索引兜底

### 量化结果

在正式 `flash-sustain` 压测场景里：

- `500` JMeter 线程
- `5s` Ramp-Up
- `60s` 持续压测

结果是：

- 秒杀接口入口吞吐稳定在 `577~585 req/s`
- `3.4w+` 总请求里最终只有 `100/500` 个进入成功链路
- 最终实现了 `0` 超卖、`0` 重复有效订单

### 推荐面试表述

“我没有把防超卖和一人一单完全压在 MySQL 上，而是先用 Redis + Lua 在入口完成库存校验和资格预占，再用 Consumer 侧的 Redisson 用户锁和数据库唯一索引做二次保护，这样既保住了正确性，也把大量失败请求挡在了数据库之外。”

## 2. 秒杀流程优化：Kafka 异步削峰

### 痛点

做完 `Redis + Lua` 之后，我发现还剩一个问题：

- 失败请求确实挡住了
- 但成功请求还是同步写库

也就是说，系统虽然入口变轻了，但成功链路仍然会压在前台线程和数据库事务上。

### 可能方案

这里我考虑过两类方案：

1. 保持同步落库
- 实现简单
- 但高峰期前台线程阻塞明显

2. 引入消息队列异步落库
- 前台更快返回
- 可以削峰
- 但要处理消息丢失、重复消费和积压问题

### 最终选择

我最终引入了 `Kafka`，把成功请求改造成：

- Redis 资格预占
- pending-send 登记
- Kafka 异步投递
- Consumer 异步落库

### 为什么这样选

因为 MQ 的核心价值不是减少数据库总工作量，而是把工作从“同步阻塞”改成“异步排队消化”。

当前实现里，成功请求的流程是：

1. Lua 成功后先生成 `orderId`
2. 先把消息登记到 Redis pending-send
3. 再发 Kafka
4. Consumer 在用户锁保护下异步创建订单

这样做有两个好处：

- 前台线程不需要同步完成全部落库逻辑
- 如果 Kafka 首发失败，还有补偿空间

### 量化结果

当前正式压测里，秒杀接口入口吞吐稳定在 `500+ req/s`。  
但我不会把这个数字直接吹成“MQ 一定更快”，因为当前环境是：

- 单机
- 单 Redis
- 单 Kafka broker
- 单 partition

所以我更强调它的意义是：

- 成功请求进入了可异步、可补偿、可恢复的链路
- 最终库存和订单保持一致

### 推荐面试表述

“我引入 Kafka 的目标不是单纯追求一个更高的单机 QPS，而是把成功请求从同步写库改造成可排队、可补偿、可恢复的异步链路，真正解决成功请求消化的问题。”

## 3. Kafka 投递失败补偿与消费幂等

### 痛点

引入 MQ 后，如果只会“发消息”，其实还不够，因为会遇到：

- Redis 已预占成功，但 Kafka 首发失败
- 消息重复投递或重复消费
- Kafka 短时异常后如何恢复

### 可能方案

我考虑过更重的事务消息 / Outbox 思路，但当前项目更希望：

- 方案实现成本可控
- 能在现有技术栈里快速落地
- 同时补上最关键的一致性缺口

### 最终选择

我最终做的是一套轻量的 Redis pending-send 补偿方案。

Redis 里会维护：

- `seckill:pending:send:{orderId}`
  - 保存消息明细
- `seckill:pending:send:index`
  - ZSet 索引，按 `nextRetryAt` 扫描补发

### 为什么这样选

原因是：

- 它实现简单
- 和当前 Redis 技术栈契合
- 能解决“资格已占用但消息没发出去”的关键问题

Consumer 幂等方面，我也做了多层控制：

- `Redisson RLock`
- 订单状态判断
- 数据库唯一索引

### 量化结果

这部分没有直接写成一个单独的“吞吐提升数字”，但它支撑了两个最终结果：

- 异步链路最终能 `drain` 排空
- 秒杀最终仍然保持 `0` 超卖、`0` 重复有效订单

### 推荐面试表述

“我这里没有上完整的事务消息方案，而是做了一个轻量的 Redis pending-send 补偿层，优先解决 Redis 已预占但 Kafka 首发失败时的状态悬挂问题；再结合 Consumer 侧用户锁、订单状态机和唯一索引，保证异步链路最终一致且具备幂等性。”


### 选型：Redis pending-send or 完整的事务消息方案（如Outbox）

系统需要保证 **MySQL 数据变更与 Kafka 消息发送的一致性**，避免出现：

* 数据库更新成功，但 Kafka 消息丢失；
* Kafka 消息发送成功，但业务数据未提交；
* 服务重启、Kafka 故障导致消息永久丢失。

可靠性要求较高，涉及订单、库存、支付等核心业务场景。

---

### 方案对比

#### 方案一：Redis Pending List

实现思路：

* 业务数据写入数据库；
* Kafka 发送失败时，将消息写入 Redis Pending List；
* 后台任务持续重试发送。

优点：

* 实现简单；
* 接入成本低；
* 性能较好。

缺点：

* 无法保证数据库事务与 Redis 操作的原子性；
* 存在数据库成功但 Redis 写入失败导致消息丢失的风险；
* Redis 并非业务数据的最终可信来源（Source of Truth）；
* 难以从根本上解决数据与消息的一致性问题。

适用场景：

* 缓存刷新；
* 埋点统计；
* 邮件、短信通知等允许少量消息丢失的业务。

---

#### 方案二：Outbox Pattern

实现思路：

* 在业务事务中同时写入业务表和 Outbox 表；
* 事务提交后，由独立任务扫描 Outbox 表并发送 Kafka；
* 发送成功后更新 Outbox 状态。

优点：

* 业务数据与待发送消息处于同一数据库事务；
* 保证“业务成功则消息一定存在”；
* Kafka 不可用时消息不会丢失；
* 支持幂等重试；
* 属于业界成熟方案，可与 CDC、Debezium 等方案结合。

缺点：

* 需要额外维护 Outbox 表；
* 增加消息投递流程和状态管理；
* 实现复杂度高于 Redis Pending List。

适用场景：

* 订单系统；
* 支付系统；
* 库存系统；
* 账户系统；
* 需要保证最终一致性的核心业务。

---

### 最终选型

经过评估，最终选择 **Outbox Pattern** 方案。

选择依据：

1. **能够保证业务数据与消息记录的事务一致性**；
2. **避免数据库成功而消息丢失的问题**；
3. **Kafka 故障或服务重启场景下仍可恢复投递**；
4. **符合微服务领域解决事务消息问题的最佳实践**；
5. **相比 Redis Pending List，可靠性和可维护性更高**。

---

### 最终架构

```text
业务服务
    │
    ▼
MySQL事务
├── 业务表
└── Outbox表
    │
    ▼
Outbox Dispatcher
    │
    ▼
Kafka
    │
    ▼
消费者
```

其中 Outbox 表作为消息的持久化存储和唯一可信来源，Kafka 仅负责消息传递，从而实现业务数据与消息发送的最终一致性。

## 4. 未支付订单自动关闭与库存回补

### 痛点

秒杀下单成功不代表用户一定会支付。  
如果超时订单不自动关闭，就会出现：

- 库存被长期占用
- 后续用户无法正常购买
- 资格也无法恢复

### 可能方案

我考虑过三类方案：

1. 纯 `Spring Task` 扫描数据库
- 实现简单
- 但时效性依赖扫描频率

2. MQ 延迟消息
- 能更贴近到期时间
- 但引入更重的中间件能力

3. `Redisson` 延迟队列
- 和当前 Redis 技术栈契合
- 实现相对轻量
- 再配合低频定时任务兜底

### 最终选择

最终我选的是：

- `Redisson RDelayedQueue` 作为主路径
- `Spring Task` 低频扫描作为兜底

### 为什么这样选

因为我的目标不是上最重的架构，而是找到一个：

- 和现有项目契合度高
- 实现复杂度适中
- 时效比纯扫描更好

的方案。

具体逻辑是：

1. 订单创建成功后投递超时消息
2. 到期后延迟队列消费关单
3. 如果延迟队列异常，低频扫描兜底

关单成功后，我还做了完整回补：

- 数据库库存回补
- Redis 库存回补
- 删除 `seckill:order:{voucherId}` 中的用户资格占用
- 写入 `seckill:reorder:{voucherId}:{userId}`

### 量化结果

在统一的 `100 单 / 15 秒超时` 压测口径下：

- `FALLBACK_ONLY`：`P95 = 4055ms`
- `DELAY_QUEUE_FALLBACK`：`P95 = 533ms`

时效提升约 `86.9%`。

同时这一轮结果里：

- `P50 = 26ms`

说明大多数订单在到期后几十毫秒内就完成了自动关闭。

### 推荐面试表述

“我没有只做一个定时扫描关单，而是用了 Redisson 延迟队列做主路径、Spring Task 做兜底，这样既兼顾时效性，又保留异常场景下的补偿能力。正式压测下，自动关单 `P95` 延迟从 `4055ms` 压到了 `533ms`。”

## 5. 支付与关单的并发控制

### 痛点

支付回调和超时关单本质上是在竞争更新同一笔订单状态。

如果处理不好，会出现：

- 支付成功了又被关单
- 已关单订单又被支付成功覆盖
- 重复回补库存

### 可能方案

这里可以用两类思路：

1. 悲观锁
- 保证强控制
- 但会串行化

2. 基于状态条件更新的乐观并发控制
- 让请求并发竞争
- 谁先改成功谁生效

### 最终选择

我最终选的是：

- 基于订单状态条件更新的 CAS 风格控制

### 为什么这样选

因为支付和关单的冲突点非常明确：

- 只要订单还是 `UNPAID`，某一方才能改状态

所以我让两边都走条件更新：

- `where id = ? and status = UNPAID`

谁先成功，谁拿到状态变更权。  
另一个更新影响行为 `0`，就说明状态已经被别人抢先改掉了。

这种方式的优点是：

- 不需要显式悲观锁
- 并发控制足够清晰
- 性能比串行悲观锁更好

### 量化结果

这里没有单独的吞吐指标，但它是保证以下结果成立的关键条件：

- 不会双重回补库存
- 支付和关单最终只会有一个终态成功

### 推荐面试表述

“这里我没有额外加悲观锁，而是用基于订单状态的条件更新做并发控制，本质上是一个轻量的 CAS 思路，既避免了状态覆盖，也避免了串行锁带来的额外开销。”

---

## 6. 缓存击穿治理：逻辑过期

### 痛点

热点数据缓存过期时，如果大量请求同时回源数据库，就会出现缓存击穿。

### 可能方案

我考虑过两种典型方案：

1. 互斥锁重建
- 一致性更强
- 但高并发下会有线程等待堆积

2. 逻辑过期
- 请求先返回旧值
- 异步重建缓存
- 可用性更好

### 最终选择

我最终对热点店铺缓存采用的是：

- 逻辑过期
- 后台异步重建
- 再配一个轻量互斥锁防止重复重建

### 为什么这样选

因为这个场景是：

- 读多写少
- 短时间读到旧值可以接受
- 更看重可用性和响应延迟

所以相比强一致性的互斥锁重建，我更愿意接受短暂弱一致，换取更平稳的高并发表现。

### 推荐面试表述

“对热点缓存击穿，我没有选强阻塞式的互斥锁重建，而是选了逻辑过期，因为这个业务更看重可用性和低延迟，短时间旧值是可以接受的。”

---

## 7. 缓存穿透治理：布隆过滤器 + 空值缓存

### 痛点

如果用户持续请求不存在的 `shopId`，请求会绕过缓存不断打数据库，这就是缓存穿透。

### 可能方案

我考虑过：

1. 只做参数校验
- 实现简单
- 但只能挡掉格式错误请求

2. 只做缓存空值
- 能挡住重复非法请求
- 但第一次非法请求仍然会打 DB

3. 布隆过滤器 + 缓存空值
- 布隆负责前置拦截明显不存在的数据
- 空值缓存负责兜住已经穿透过一次的请求

### 最终选择

我最终采用的是：

- `RBloomFilter + 缓存空值`

### 为什么这样选

因为两者组合比单独用一个更稳：

- BloomFilter 负责尽量在入口挡住非法 ID
- 空值缓存负责兜底，处理那些已经打到 DB 的不存在数据

### 量化结果

在纯非法 `shopId` 请求场景下：

- `OFF` 模式：`DB fallback = 26`，`P95 = 114ms`
- `BLOOM_NULL` 模式：`DB fallback = 0`，`P95 = 91ms`

也就是：

- 数据库回源从 `26` 次降到 `0`
- 查询 `P95` 从 `114ms` 优化到 `91ms`

### 推荐面试表述

“我这里不是只做了缓存空值，而是用 RBloomFilter 加缓存空值做组合防护。这样既能前置拦截明显不存在的数据，也能把已经穿透过一次的非法请求挡在缓存层。正式压测下，纯非法请求场景的 DB 回源从 `26` 次降到了 `0`。”

---

## 8. 缓存一致性：旁路缓存 + MQ 补偿重试

### 痛点

更新数据库后如果删缓存失败，就可能产生脏缓存。

### 可能方案

我考虑过：

1. 延迟双删
- 思路常见
- 但实现上时序不稳定

2. Canal / Binlog 订阅
- 解耦更彻底
- 但实现和运维成本更高

3. 旁路缓存 + MQ 补偿重试
- 业务代码直接可控
- 和现有 Kafka 技术栈更契合

### 最终选择

我最终采用的是：

- 更新数据库后删除缓存
- 如果删除失败，发送 Kafka 补偿消息
- 再加 TTL 兜底

### 为什么这样选

因为当前项目是一个中小规模后端项目，我更看重：

- 实现成本可控
- 链路清晰
- 便于讲清楚一致性思路

Canal 当然更解耦，但对这个项目来说会显得太重。

### 推荐面试表述

“我这里采用的是典型的旁路缓存模式，但不是只做到‘更新数据库后删缓存’就结束，而是继续补了 Kafka 删除失败补偿和 TTL 兜底，让这个方案更完整。”

## 四、最后总括怎么讲

如果面试官让我最后用一段话总结，我会这么说：

“这个项目我最核心的工作，不是简单把秒杀接口跑通，而是把系统从同步写库一步步演进成 Redis 前置过滤、Kafka 异步削峰、MySQL 最终一致性落库的完整闭环。Lua 负责原子校验库存和一人一单，Kafka 负责把成功请求从同步写库改造成可排队、可补偿、可恢复的异步链路，Redisson 延迟队列负责未支付订单超时关闭，BloomFilter 和缓存空值负责处理缓存穿透。最终我通过压测拿到了几组关键结论：秒杀主链路实现了 `0` 超卖和 `0` 重复有效订单，纯非法请求场景下 DB 回源从 `26` 次降到 `0`，自动关单 `P95` 从 `4055ms` 压到了 `533ms`。我觉得这个项目最能体现的，不只是某一个 QPS 数字，而是我把高并发秒杀里的状态机、补偿和最终一致性闭环真正补完整了。”
