

开始具体讲之前先阐述一下业务背景或者场景需求：
针对本地生活优惠券秒杀场景，目前的痛点是活动开始瞬间流量集中、库存热点竞争严重、用户重复下单风险高，对系统吞吐和可用性要求高，对个别非核心查询的强一致性要求不高，总体架构采用“Redis前置拦截 + 消息队列削峰异步落库 + MySQL最终落地”的分层设计

我们要设计一个高并发秒杀系统，主要考虑逐层过滤的方案，前端限流（抗流量）+CDN缓存+Redis缓存（抗读写）+消息队列削峰+数据库兜底和最终落地
同时通过集群、数据持久化、降级等方案保证高可用，通过旁路缓存、数据库唯一索引、消息补偿重试等方案保证数据一致性

话术原则，对于自己不熟悉的技术点和方案少提及，面试官大概率会追问

主要职责：
	秒杀防超卖和一人一单：使用Redis存储库存和订单信息，用Lua脚本判断用户下单资格，保证库存不超卖和一人一单；

首先没有引入Redis，尝试使用MySQL实现防超卖和一人一单（库存扣减时使用乐观锁思想，update时加上where stock > 0 条件，即
UPDATE seckill_voucher 
SET stock = stock - 1 
WHERE voucher_id = ? AND stock > 0;
先加分布式锁再查用户是否已经下过单，并建立(voucher_id+user_id)唯一索引（兜底）防止一人多单）

对于乐观锁，update的行锁导致串行竞争严重（缺点），虽然单个 UPDATE 内部原子，但每个请求从“加锁 → 读 → 写 → 释放锁”仍需要几十微秒到几百微秒，加上网络和 SQL 解析，整体 QPS 上限就是几千，存在严重性能瓶颈，
乐观锁只能保证库存不超卖，无法保证一人一单，需要将二者放在同一事务中进行，同时成功或者失败，先判断一人一单，再用乐观锁扣减库存，但这样仍然会存在高并发下大量请求直接打到数据库、热点行竞争激烈、整体吞吐上不去的问题
所以添加了Redis缓存，测试发现请求先在 Redis 层完成资格校验后，数据库压力明显下降，秒杀链路的响应速度和系统吞吐都更稳定

Redis先吸收高并发洪峰，完成资格校验和下单，MySQL异步再进行一次资格校验与下单，保证最终一致性
我这里不是只靠 Lua 做一人一单，而是做了三层保护。第一层是在 Redis 入口用 Lua 原子校验库存和一人一单，防止高并发请求同时抢到资格；第二层是在 Kafka 消费落库时按 userId 加 Redisson 分布式锁，防止消息重复消费或多实例并发时重复创建订单；第三层是在数据库层通过唯一索引做最终兜底，保证即使前两层在极端情况下失效，也不会出现同一用户重复下单

之所以引入 Redis 和 Lua，不是因为 MySQL 完全做不到，而是因为秒杀场景不只是库存不能小于 0，还要考虑一人一单、热点行竞争、数据库抗压和异步削峰。MySQL 可以保证正确性，但高并发下所有请求都直接打到数据库，会形成严重的行锁竞争；Redis + Lua 更大的价值是在内存里先完成库存和资格校验，把大部分无效请求 拦在数据库之外，再通过消息队列异步落库。



	秒杀流程优化：修改同步流程，用户下单后使用消息队列异步处理库存扣减和订单生成，提高秒杀场景的并发性能；

同步流程有接口阻塞时间长、请求线程占用高、数据库瞬时写压力大等缺点，异步后用户线程只负责资格校验和发送消息，真正的落库放到消费端处理，峰值流量被消息队列削平，系统吞吐和稳定性更好，前后压测数据对比可以重点体现数据库压力下降、平均响应时间缩短、秒杀成功链路更稳定
异步落库通过“Redis预扣资格 + Kafka异步落库 + Redisson锁防重复消费 + 数据库唯一索引兜底”保证最终一致性和消费幂等性

但是目前采用的单broker单partition的单节点消息队列，未能发挥其全部作用，对缓解数据库写压力的作用有限


	订单超时关闭与库存回流：引入Redisson延迟队列+低频Spring Task定时任务兜底实现未支付订单的到期自动关闭；

如何实现超时订单自动关闭，我调研了常见的几种方案：
方案一：每分钟执行定时任务：扫描MySQL数据库 取出未支付且超时的订单
方案二：利用消息队列的延迟消息，在订单创建时发送延迟消息，在一定时间后，消息被消费关单
方案三：利用 Redisson 延迟队列

优劣分别为：定时任务实现简单但轮询数据库压力较大、时效性一般；MQ 延迟消息解耦更好但引入的中间件能力更重、实现和运维成本更高；Redisson 延迟队列实现相对轻量，和当前项目 Redis 技术栈契合度高，业务需求更看重快速落地、实现复杂度可控和分钟级内的准实时关单，最终选择了 Redisson 延迟队列方案，辅以被动关单的机制（用户查看订单状态时触发检查操作，若过期则关单，再返回订单状态给用户）

这里使用 Redisson 而不是用 RocketMQ 的原因有两点：

1.RocketMQ 虽然本身支持延迟消息，但当前项目已经依赖 Redis，没有必要为了超时关单再额外引入一套更重的 MQ 能力，Redisson 的实现更轻量。
2.当前业务规模下，Redisson 延迟队列已经能满足超时关单的需求，再加上 Spring Task 兜底，整体实现成本和收益更匹配。

如何处理订单取消回滚，核心是先基于订单状态 CAS 把未支付订单更新为已取消，更新成功后再回补 MySQL 秒杀库存，同时回补 Redis 中预扣的库存，并删除该用户在 Redis 里的下单标记，保证后续还能重新参与活动

	支付与关单的并发：使用乐观锁（基于订单状态条件更新（CAS））解决订单支付和关单的并发问题；

解决思路：加互斥锁锁住该订单（一锁二判三更新）或乐观锁
考虑到支付和关单本质上是对同一订单状态做竞争更新，冲突点很明确，而且我更希望减少加锁带来的串行化和额外开销，最终选择了乐观锁方案，保证并发下的一致性

从实现形式上看，它确实就是一条普通 update，但关键点不在 SQL 形式，而在并发控制语义。我没有先加锁把并发操作串行化，而是让支付和关单都去竞争更新同一个订单状态，只在更新时加 status = 未支付 这个前置条件。谁先更新成功，谁就抢到状态变更权；另一个更新影响行数为 0，就知道订单状态已经被别人修改了。这本质上是一种基于状态条件的 CAS，也可以理解成轻量级的乐观并发控制，而不是 version 字段那种标准乐观锁实现


	缓存优化：使用逻辑过期方案防止Redis热点Key的缓存击穿问题；使用缓存空值方案解决Redis Key的缓存穿透问题；

对缓存击穿问题：
先考虑互斥锁方案，重建缓存时需要先获取互斥锁（没抢到锁的后续流程：先判断缓存是否重建，若未重建则短暂休眠后重试或直接返回旧值），保证强一致性，但遇到了高并发下等待线程堆积、接口延迟抖动明显、可用性受到影响的问题。
因此考虑逻辑过期方案，判断key过期后开启一个异步线程去重建缓存（为了避免多个线程同时重建，还是需要再抢一把互斥锁，只让拿到锁的线程真正执行重建），其他线程直接返回旧数据，更好地保证了服务的可用性，牺牲了一定的一致性，但因为这里的业务需求是店铺信息这类读多写少、短时间旧数据可接受的场景，更看重高可用和低延迟，且不一致时间通常只出现在缓存重建的短暂窗口内，所以最终选择了逻辑过期方案。

对缓存穿透问题：
了解到常见解决方案为入口参数校验/布隆过滤器/缓存空值，比较之下发现：入口参数校验实现简单，但只能拦截一部分非法请求；布隆过滤器适合在入口大规模拦截不存在的 key，但存在误判；缓存空值可以兜住已经穿透到数据库的不存在数据。最后采用了布隆过滤器+缓存空值的组合防护体系，再配合基础参数校验形成多层防护。


	数据一致性保证：采用旁路缓存模式，更新数据库后删除缓存，若删除失败消息队列补偿重试，TTL兜底共同保证数据一致性；
权衡

开始考虑旁路缓存或者延迟双删方案，前者数据库压力更小（缓存为null时间更短，但可能读到旧数据），后者数据一致性更好（两次删除可能产生缓存击穿和穿透，但更不容易读到旧数据）

因为当前项目写操作频率不高，而且我希望更新链路尽量简单可控，所以没有采用延迟双删
开始采用旁路缓存，但可能缓存删除失败造成数据不一致，考虑使用canal监听数据库变更日志binlog或引入消息队列重试机制。
canal监听优点是和业务代码解耦、可以统一监听数据库变更；缺点是要额外维护canal实例和binlog链路，实现和运维成本更高，问题排查也更复杂
Kafka消息队列重试优点是实现直接、和现有项目技术栈契合、补偿逻辑更容易按业务定制；缺点是仍然需要业务自己处理重试次数、失败告警和最终兜底
我们的场景是中小规模本地生活项目，写流量不算特别高，更看重实现成本可控、链路清晰和便于后续面试讲解，所以最终选择了消息队列重试方案
