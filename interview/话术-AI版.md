# 生活优选 - 高并发秒杀系统设计与优化

## 项目概览

- 时间：2025.08 - 2025.10
- 项目描述：生活优选是一个面向本地生活场景的优惠营销平台，围绕商户信息展示、优惠券领取与秒杀下单等核心功能展开，既为用户提供便捷的优惠消费入口，也帮助商家完成活动推广与流量转化。
- 技术栈：Spring Boot + MySQL + Redis + MyBatis-Plus + Lua + Redisson

## 简历描述

- 设计并实现高并发秒杀链路，基于 Redis 存储库存和下单状态，结合 Lua 原子校验库存与下单资格，保障库存不超卖和一人一单。
- 将秒杀下单流程由同步改造为异步，基于消息队列完成削峰与异步落库，降低数据库瞬时写压力，提升秒杀场景下的系统吞吐能力。
- 设计订单超时关闭与库存回流机制，引入 Redisson 延迟队列并结合定时任务兜底，保障未支付订单自动关闭和库存及时回补。
- 针对支付回调与超时关单并发冲突，采用基于订单状态条件更新的 CAS 机制，保证并发场景下订单状态流转正确。
- 封装缓存组件，采用逻辑过期方案缓解热点 Key 缓存击穿，提升高频读场景下的访问稳定性。
- 使用布隆过滤器 + 缓存空值组合方案拦截非法与不存在请求，降低缓存穿透带来的数据库访问压力。
- 采用旁路缓存模式保证缓存与数据库一致性，并通过 MQ 补偿重试和 TTL 兜底，降低缓存删除失败带来的不一致风险。

## 开场话术

开始具体讲之前，我一般会先交代业务背景。这个项目本质上是一个本地生活优惠券秒杀场景，流量会在短时间内集中到少量热点商品上，所以核心问题不是普通的增删改查，而是高并发下的库存正确性、一人一单约束、数据库抗压能力，以及缓存和异步链路的一致性控制。

这个场景对吞吐、响应时间和可用性要求很高，但对极短时间的数据延迟容忍度相对更高，所以整体架构采用的是逐层过滤思路：前端限流和静态资源缓存先挡住一部分流量，请求进入服务后由 Redis 做热点数据承接和资格校验，再通过消息队列异步削峰，最后由 MySQL 做最终落库和结果收敛；同时配合集群部署、数据持久化、超时兜底和补偿机制保证高可用与最终一致性。

## 话术原则

- 先讲业务痛点，再讲为什么选这个方案，不要一上来堆技术名词。
- 先讲方案权衡，再讲最终落地，体现你不是“背答案”，而是真的做过取舍。
- 对于压测数据，如果没有非常准确的数字，就讲优化前后的瓶颈变化和趋势，不硬编数据。

## 详细话术

### 1. 秒杀防超卖和一人一单

**优化后的贡献描述**

使用 Redis 存储库存和下单状态，结合 Lua 脚本原子校验用户下单资格，保证库存不超卖和一人一单。

**话术展开**

我一开始先尝试用 MySQL 直接实现防超卖和一人一单。库存扣减时用了乐观锁思路，也就是在更新语句里加 `stock > 0` 条件：

```sql
UPDATE seckill_voucher
SET stock = stock - 1
WHERE voucher_id = ? AND stock > 0;
```

然后再通过“先加锁、再查订单”的方式控制一人一单，必要时再加 `(voucher_id, user_id)` 唯一约束做数据库兜底。

这个方案的优点是实现直接、正确性强，所有核心判断都收敛在数据库事务里；但缺点也很明显。第一，秒杀券会形成热点行，所有请求都去竞争同一行库存，数据库很容易成为瓶颈；第二，一人一单判断、库存扣减和订单创建都依赖数据库交互，链路长、锁持有时间长，在高并发下吞吐很快触顶；第三，乐观锁只能很好地解决库存不超卖，但如果要同时保证一人一单，就必须把“查重 + 扣减 + 创建订单”尽量收敛在同一个事务链路里，这会进一步放大数据库压力。

所以后来我把资格校验前移到了 Redis。Redis 先承接高并发流量，Lua 脚本在内存里原子完成库存判断、一人一单判断和下单资格确认，把绝大多数无效请求拦在数据库之外，再由后续异步流程完成订单落库。

这里我一般会强调不是“只靠 Lua 就完事了”，而是做多层保护。第一层是 Redis 入口的 Lua 原子校验，避免并发请求同时抢到资格；第二层是异步消费下单消息时，再按用户维度做并发控制，避免重复消费或并发落库导致重复订单；第三层是数据库唯一约束兜底，保证即使前两层在极端情况下失效，也不会出现同一用户重复下单。

之所以引入 Redis 和 Lua，不是因为 MySQL 做不到，而是因为秒杀场景除了正确性，还要考虑热点竞争、抗压能力和削峰能力。MySQL 更适合做最终事实存储，Redis 更适合做高并发入口的快速过滤。

### 2. 秒杀流程优化

**优化后的贡献描述**

将秒杀流程由同步下单改造为异步下单，基于消息队列实现削峰与异步落库，提升秒杀场景下的并发处理能力。

**话术展开**

同步流程的问题主要在于链路太长。用户发起下单请求后，请求线程要同步完成资格校验、库存扣减、订单查重、订单写库等一系列操作，这意味着大量请求会直接阻塞在数据库写入和锁竞争上，接口响应时间会快速升高。

所以我把同步流程改成了异步流程。请求线程只负责完成资格校验和下单请求入队，校验通过后就立即返回下单结果或订单 ID；真正的库存扣减和订单落库放到消息队列消费者里异步执行。这样做的核心价值是把数据库写压力从用户主链路里拆出来，让 Redis 和消息队列先吸收高并发洪峰，再由后端消费者按可控节奏落库，实现削峰填谷。

如果面试官问同步和异步的差别，我会这样答：同步模式下，请求线程会被数据库操作阻塞，峰值流量一上来，连接池、线程池和数据库都会承压；异步模式下，请求线程只做快速校验和投递消息，主链路延迟明显降低，系统吞吐更高，也更稳定。

如果面试官追问异步落库怎么保证一致性和幂等性，我会分两层回答。第一层是一致性：消息队列方案本质上保证的是最终一致性，而不是强一致性，也就是说用户抢券成功后，订单最终会异步写入数据库；第二层是幂等性：消费端要基于业务唯一键做去重校验，比如按用户 ID 和优惠券 ID 判断是否已经生成过订单，同时配合分布式锁或唯一约束，防止重复消费造成重复下单。

如果要讲完整流程，我会概括成：用户请求秒杀 -> Redis/Lua 做原子资格校验 -> 校验通过后写入消息队列 -> 消费者异步扣减库存并创建订单 -> 消费成功后确认消息，失败则进入重试或补偿流程。

### 3. 订单超时关闭与库存回流

**优化后的贡献描述**

设计订单超时关闭与库存回流方案，使用 Redisson 延迟队列结合定时任务兜底，实现未支付订单自动关闭和库存回补。

**话术展开**

对于超时订单自动关闭，我调研过三种比较常见的方案。

第一种是定时任务扫描 MySQL，定期查找未支付且已超时的订单，再批量关单。这种方案实现简单，但是实时性一般，而且随着订单量增大，扫表压力会越来越明显。

第二种是使用消息队列延迟消息。下单时就投递一条延迟消息，到时间后消费消息并关闭订单。这个方案实时性更好，也符合异步解耦思路，但前提是系统已经引入了比较成熟的 MQ 体系，同时还要考虑消息堆积、延迟漂移和额外运维成本。

第三种是使用 Redisson 延迟队列。它的优点是接入成本低，和现有 Redis 体系天然兼容，比较适合中小型系统快速落地；缺点是如果后续业务继续扩张，调度能力和可观测性一般不如专业消息中间件。

综合权衡后，我更倾向使用 Redisson 延迟队列作为主方案，再配一个低频 Spring Task 做兜底扫描。业务上更看重的是实现复杂度可控、延迟精度够用，以及能够快速接入当前架构，而不是一开始就为了超时关单单独引入一整套 MQ 体系。

另外我还会补一个被动关单机制，也就是用户在查询订单状态时，如果发现订单已超时但还未被后台任务关闭，就在查询链路里触发一次状态检查和关单操作，再把最新状态返回给用户，这样可以进一步降低极端情况下的漏关单概率。

如果面试官问为什么这里用 Redisson 而不是 RocketMQ，我会回答两点。第一，RocketMQ 虽然支持延迟消息，但一旦消息堆积，实际触发时间可能和预期有偏差；第二，Redis 在项目里本身就是核心依赖，引入 Redisson 的成本更低，也能减少额外中间件依赖。

如果追问订单取消后怎么回滚 MySQL 和 Redis，我会这样说：订单状态变更以 MySQL 为准，先通过事务把订单改成已取消，同时回补数据库库存；Redis 库存不做分布式事务强绑定，而是通过补偿消息或重试任务做最终回补。也就是说，先保证数据库事实正确，再通过异步补偿把 Redis 修正回来。

### 4. 支付与关单的并发

**优化后的贡献描述**

使用基于订单状态条件更新的 CAS 机制，解决订单支付与超时关单并发执行时的状态竞争问题。

**话术展开**

支付和关单本质上是两个并发修改同一订单状态的操作。如果处理不好，就可能出现“用户已经支付成功，但后台仍然把订单关掉”这种状态错乱问题。

我当时考虑过两种方案。一种是加互斥锁，把同一订单的支付和关单串行化；另一种是用乐观并发控制，也就是基于订单当前状态做条件更新。

最终我更倾向选择后者，因为支付和关单其实都是对单行状态做竞争更新，没有必要为了这类轻量状态流转引入重量级锁。具体做法是：支付时只允许把“未支付”更新成“已支付”，关单时也只允许把“未支付”更新成“已取消”。谁先更新成功，谁就拿到状态变更权；另一个操作更新影响行数为 `0`，就说明订单状态已经被改过，后续不再继续执行。

从 SQL 形式上看，它就是一条普通的条件更新：

```sql
UPDATE tb_voucher_order
SET status = 2, pay_time = NOW()
WHERE id = ? AND status = 1;
```

关单逻辑也是同样的思路：

```sql
UPDATE tb_voucher_order
SET status = 4, update_time = NOW()
WHERE id = ? AND status = 1;
```

它的关键不是 SQL 写法本身，而是并发控制语义。我没有先加锁把并发操作串行化，而是让支付和关单都去竞争同一个状态变更条件，本质上就是一种基于状态条件的 CAS，也可以理解成轻量级的乐观锁方案。

### 5. 缓存优化

**优化后的贡献描述**

使用逻辑过期方案缓解热点 Key 的缓存击穿问题，使用布隆过滤器 + 缓存空值方案防止缓存穿透，并对多种缓存保护策略进行了对比和权衡。

**话术展开**

对于缓存击穿问题，我最开始先考虑的是互斥锁方案。也就是热点 Key 失效后，只允许一个线程去重建缓存，其他线程等待或重试。这个方案的一致性比较强，但在高并发热点场景下，没拿到锁的线程会持续等待，容易出现响应变慢、线程堆积，严重时还可能表现出短时不可用。

所以后来我更倾向用逻辑过期方案。它的思路是缓存数据本身不立刻删除，而是在 value 里带一个逻辑过期时间。请求进来后，如果发现未过期，就直接返回；如果发现已经过期，就由一个线程去异步重建缓存，其他线程先返回旧数据。这样能更好地保证服务可用性，代价是会有很短时间的数据不一致。

如果面试官追问“怎么确定哪个线程去重建，是否还要抢锁”，我会回答：逻辑过期方案通常仍然会配合一把互斥锁使用，但这把锁不是为了阻塞所有请求，而只是为了控制只有一个线程负责缓存重建。谁先抢到锁，谁就负责异步刷新缓存，其他线程直接返回旧数据。

最终我之所以选择逻辑过期，是因为这里的业务数据更偏查询型，比如店铺详情、商户信息这类数据，对绝对强一致要求没那么高，更看重高并发下的可用性和响应稳定性。而且逻辑过期带来的不一致时间通常很短，一般就是一次缓存重建的窗口期。

对于缓存穿透问题，我了解过几种常见方案，包括入口参数校验、布隆过滤器和缓存空值。参数校验适合过滤明显非法请求，但挡不住那些“参数合法但数据不存在”的访问；布隆过滤器适合在入口提前拦截大量不存在的数据请求，减少无效流量穿透到 Redis 和数据库；缓存空值则适合兜住少量漏判或首次穿透请求，实现成本低，也便于和现有缓存体系结合。

所以最后我会选择“入口参数校验 + 布隆过滤器 + 缓存空值”的组合方案。测试方式也比较直接，可以构造一批不存在的 ID 反复请求，对比引入布隆过滤器和空值缓存前后的数据库命中次数、Redis 命中情况和 QPS 变化。通常会发现，大部分无效请求会先被布隆过滤器拦住，少量漏过的请求再由缓存空值兜底，数据库压力会明显下降。

### 6. 数据一致性保证

**优化后的贡献描述**

采用旁路缓存模式，更新数据库后删除缓存，并通过消息队列补偿重试和 TTL 兜底，降低缓存与数据库不一致风险。

**话术展开**

缓存一致性这块，我采用的是比较经典的旁路缓存模式，也就是“先更新数据库，再删除缓存”。这种方式实现简单，业务侵入小，也比较符合读多写少场景。

为什么没有优先选延迟双删，主要是因为它对时机比较敏感。第二次删除如果太早，可能挡不住并发读；如果太晚，又会增加流程复杂度，而且本质上也不能完全消除并发窗口问题。所以综合下来，我更倾向“更新数据库后删除缓存”这条主链路。

但只做这一步还不够，因为删缓存也可能失败。一旦数据库更新成功、缓存删除失败，就可能产生脏数据。所以我又补了两层保障。第一层是 TTL 兜底，即使缓存没删掉，脏数据也不会永久存在；第二层是补偿机制，也就是把删除缓存失败事件投递到消息队列里，由消费者异步重试删除，直到成功或进入告警处理。

如果面试官追问为什么不用 Canal 监听 binlog，我会说我确实考虑过。Canal 的优点是能直接订阅数据库变更，对业务代码侵入小，适合多服务共同操作同一份数据的场景；缺点是部署和维护成本更高，问题排查链路也更长。

而消息队列补偿方案的优点是实现更直接、链路更可控，和现有系统也更容易整合；缺点是需要业务侧自己保证消息可靠性和重试机制。结合当前场景，我更看重实现成本、落地速度和可控性，所以最终会优先选择消息队列补偿重试方案。
