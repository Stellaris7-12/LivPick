# 第一轮拷打回答

## 第一轮：整体架构与核心链路

### 面试官问题

先介绍一下你的秒杀核心链路吧。从用户点击“立即抢购”到最终订单生成，或者失败返回，请求都经过了哪些组件？用了什么同步/异步策略？

### 标准回答

我的秒杀链路可以分成四段：入口资格校验、消息投递、异步落库、超时回补。

第一段是入口资格校验。用户调用 `POST /voucher-order/seckill/{id}` 之后，服务端会先拿到 `userId`，再判断这个用户在 Redis 里有没有可复用的已取消订单，如果有就复用原来的 `orderId`，没有就生成新的 `orderId`。然后执行 `seckill.lua` 脚本，脚本里会原子完成三件事：判断库存是否大于 0、判断用户是否已经在 `seckill:order:{voucherId}` 这个集合里、如果都通过就扣减 `seckill:stock:{voucherId}` 并把用户写进下单集合。这里是同步的，因为我要在入口就把“库存不足”和“一人一单”挡掉。

第二段是消息投递。Lua 返回成功后，我会先把这次秒杀消息注册到一个 pending-send 结构里，相当于先留下“待发送凭据”，然后再往 Kafka 发 `SeckillOrderMessage`。消息体里当前包含 `orderId`、`userId`、`voucherId`、`createTime`。这一步对用户来说还是同步返回的，但真正的订单创建已经从同步写库改成异步链路了。

第三段是异步落库。Kafka Consumer 收到消息后，会按 `userId` 维度加 Redisson 分布式锁，避免同一个用户被重复消费或并发落库。然后它会查这个用户这张券在数据库里是否已有订单：如果没有，就扣减数据库库存并创建 `UNPAID` 订单；如果有一条 `CANCELLED` 且 `orderId` 正好匹配这次消息，就走“重激活已取消订单”的分支；如果已经有有效订单，就把它当成重复或脏消息直接跳过。落库成功后，再给这笔订单投递一个超时关单消息。

第四段是超时回补。订单创建后，我会通过 Redisson 的 `RDelayedQueue` 投递超时消息，到期后尝试把 `UNPAID` 订单改成 `CANCELLED`，同时回补 MySQL 库存、回补 Redis 库存、从 Redis 的下单集合里删掉用户、并写入一个 `seckill:reorder:{voucherId}:{userId}` 标记，让这个用户后面可以复用原订单再次抢购。如果延迟队列漏处理了，低频 `Spring Task` 会扫 `status=UNPAID and create_time < 过期时间` 的订单做兜底。

所以这个项目里我的同步和异步分工是这样的：入口资格校验和预占库存是同步完成的，真正的订单落库、超时关单和最终状态收敛是异步完成的。这样做的核心目的是把“失败请求快速拦截”，把“成功请求延后异步消化”。

### 追问回答

#### 追问 1

你说“5k 总并发，3.4w 总请求”，这个数据是怎么测出来的？并发模型是怎样的？5000 并发下 QPS 只有 500+，为什么这么低？

这个数据来自我最后一轮正式压测，不是拍脑袋估的。我的压测工具是 `JMeter 5.6.3`，外面再套了一层 PowerShell runner 做环境重置、结果汇总和 MQ drain 观测。比如 `flash-sustain-5k-100` 场景，JMeter 配的是 `500` 线程、`5` 秒 Ramp-Up、`60` 秒持续压测、无限循环但由 scheduler 到时停止；`flash-burst` 则是 `1000` 线程、`3` 秒 Ramp-Up、`10` 秒持续，模拟活动刚开始时的瞬时洪峰。`3.4w+` 总请求就是在这个持续压测窗口内 JMeter 累积打出来的请求量。

至于为什么“5000 并发”口径下实际 QPS 只有 `500+ req/s`，这里要先澄清概念。这个 `5k` 不是说有 5000 个线程同时在一台压测机上硬打，而是场景命名上表示“高反差秒杀”口径，核心目的是模拟库存很少、请求很多的活动。当前正式脚本里，`flash-sustain` 实际是 `500` 线程，`flash-burst` 实际是 `1000` 线程。QPS 没有到特别夸张，主要不是 Redis 单点先到极限，而是当前整个系统配置偏保守：单机、单 Redis、单 Kafka broker、单 partition，而且 Producer 发送 Kafka 时还是同步 `send().get(5s)`，Consumer 端也是单通道串行做完整事务，所以最终入口吞吐被整个链路形态限制住了，而不是只被 Redis 限住。

如果只看入口过滤能力，其实 `db-cache` 那一版比 `db-cache-mq` 还强。我不会硬说引入 MQ 后本机 QPS 一定更高，因为当前数据不支持这个结论。更准确的说法是：MQ 这版的价值在于把成功请求改造成了可恢复、可补偿、可观测的异步闭环，而不是把本机单节点入口吞吐做成绝对第一。

#### 追问 2

“最终仅 500 个请求进入成功链路”，这 500 个是什么意思？库存总量是多少？会不会因为异步落库失败导致成功数少于库存？

这里的“500 个请求进入成功链路”，指的是通过 Lua 资格校验、拿到下单资格并被接受处理的请求数，不是说 JMeter 一共只发了 500 个请求。以 `flash-sustain-5k-500` 为例，库存总量就是 `500`，总请求量是 `34490`，但最终 `ApiAccepted=500`，说明只有 500 个请求通过了前置资格校验，其它请求都因为库存不足或重复下单在 Redis 层被挡住了。

在理想情况下，如果库存是 `500`，这 `500` 个通过资格校验的请求应该都能最终下单成功。但这个“应该”不是靠运气，而是靠后面的补偿机制兜住。当前实现里，如果 Kafka 首发失败，我不会立刻回滚给用户失败，而是先把 pending-send 记录留着，由定时补偿任务继续重试；如果重试超过最大次数仍然失败，且数据库里确认没有形成有效订单，就会执行 Redis 资格回滚，把库存和用户资格恢复。也就是说，我要尽量避免“库存已经在 Redis 里扣掉了，但订单根本没生成”的库存黑洞。

所以是有两种可能的。第一种是补偿成功，那最终成功数仍然会追上库存量。第二种是补偿彻底失败，那我会把 Redis 里的预占资格回滚掉，而不是让库存凭空消失。换句话说，当前方案的目标不是承诺“每一个预扣成功请求都一定落库”，而是保证“要么最终成功下单，要么最终把资格和库存恢复”，避免长期不一致。

### 如果继续深挖，我会主动补充

我会主动强调这个项目最重要的设计取舍：我不是把所有事情都放到异步里，而是把“资格判断”留在同步入口，把“真正落库和状态收敛”放到异步链路。这样做的好处是用户能快速拿到“抢到/没抢到”的结果，而数据库和订单状态机的压力被后移到了可补偿、可恢复的链路里。

## 第二轮：库存预扣与防超卖（Lua + Redis）

### 面试官问题

你说用 Redis + Lua 原子化资格校验，同时完成库存预扣。请把 Lua 脚本的核心逻辑讲出来，需要包含用户资格校验、库存扣减、记录抢购成功标识。

### 标准回答

我当前的 Lua 脚本实现是比较直接的，核心就两类 key：

- 库存 key：`seckill:stock:{voucherId}`
- 用户资格 key：`seckill:order:{voucherId}`

其中库存用 `String`，用户资格用 `Set`。脚本伪代码可以概括成下面这样：

```lua
local voucherId = ARGV[1]
local userId = ARGV[2]

local stockKey = 'seckill:stock:' .. voucherId
local orderKey = 'seckill:order:' .. voucherId

if tonumber(redis.call('get', stockKey)) <= 0 then
    return 1
end

if redis.call('sismember', orderKey, userId) == 1 then
    return 2
end

redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)
return 0
```

也就是说，脚本先检查库存，再检查这个用户是否已经在当前券的下单集合里，如果都通过，就在同一个 Lua 执行上下文里扣库存并写资格标记。因为 Redis 执行 Lua 时是单线程串行的，所以这几个步骤对外表现成一个原子操作，不会出现两个请求同时看到库存充足、同时都扣成功的超卖问题。

这个脚本在我的体系里承担的是“秒杀资格预占”的职责，而不是最终事实存储。最终订单是否真的生成，还是要以后面的 Kafka 消费和 MySQL 落库为准。

### 追问回答

#### 追问 1

这个脚本里如何判断用户已经抢到过？用的是 Redis 的 Set 还是 String？如果用户一秒内重复发起请求，Lua 能防住吗？

当前实现里判断用户是否已经抢到过，用的是 `Set`，也就是 `seckill:order:{voucherId}` 这个集合。用户 ID 会被写进这个 Set 里，后续用 `SISMEMBER` 去判断是否已经占过资格。这种设计的好处是很直接，天然适合做“某个活动下这批用户是否已占位”的判断。

至于用户在一秒内甚至一毫秒内重复发请求，Lua 脚本本身就能防住，不需要依赖前端。因为这两个请求都会进入同一个 Redis 脚本执行链路，第一个请求执行成功后已经把 `userId` 写进 Set 了，第二个请求进来时 `SISMEMBER` 会返回 1，所以直接被判定成重复下单。前端限流和网关防刷当然也应该做，但它们是更外层的削峰和反作弊能力，不是我这个“一人一单”正确性的唯一保障。

#### 追问 2

如果库存扣减成功后，后续异步落库失败，比如 Kafka 宕机，会不会出现库存已扣但订单未生成的黑洞？

这是我设计里最重要的异常边界之一，所以我没有把“Lua 成功”直接等价成“订单一定创建”。当前做法是：Lua 成功后我先把这次请求注册到一个 pending-send 结构里，相当于先写一份“待发送台账”，然后再发 Kafka。Kafka 发送成功我就把 pending 清掉；如果发送失败，pending 记录会保留，由 `SeckillPendingRetryTask` 定时扫描重试。

如果补偿重试最终仍然失败，任务会再去检查数据库里有没有这笔订单，或者这个用户这张券有没有形成有效订单。如果都没有，就调用 Redis 回滚脚本，把资格和库存恢复掉。也就是说，当前实现的思路是“先补偿，补偿不成再回滚”，而不是让 Redis 预扣永久悬挂在那里。

所以短时间内是有可能出现“Redis 已经扣了，但数据库订单还没看到”的中间态，这就是最终一致性的典型表现；但最终不会长期停留在“库存被吞掉但订单不存在”的黑洞状态。

#### 追问 3

Lua 脚本里是否包含“检查用户是否在等待支付队列中”的逻辑？关单恢复资格时修改了哪个数据结构？Lua 能感知吗？

当前 Lua 脚本本身不检查“等待支付队列”这种状态，它只看两件事：库存和当前用户有没有被记录在 `seckill:order:{voucherId}` 里。也就是说，它不理解复杂的订单状态机，它只负责做最前面的资格占位。

真正让“取消后可以再抢”的，是后面的回补逻辑。当前有两种回补脚本：

- `seckill_rollback.lua`：用于订单创建前补偿失败时回滚，逻辑是 `SREM orderKey userId` 并 `INCRBY stockKey 1`
- `seckill_stock_rollback.lua`：用于超时关单后回补，逻辑是 `INCRBY stockKey 1`、`SREM orderKey userId`，并额外写一个 `seckill:reorder:{voucherId}:{userId}=orderId`

所以 Lua 能“感知”用户是否可以再次抢购，靠的不是它理解待支付队列，而是回补时已经把 Redis 的资格集合恢复了。等用户再次请求时，`SISMEMBER` 就会返回 0。同时服务端在执行 Lua 之前，还会先查 `reorderKey`，如果存在已取消订单，就复用原订单号走下一次异步链路。这就把“能否再抢”和“是否复用原订单”两个问题分开了。

### 如果继续深挖，我会主动补充

我会主动补一句：当前这个 Lua 脚本本身是“资格预占脚本”，并没有把支付中、已取消、复购这些复杂业务状态都塞进 Redis 判断。这样做的好处是脚本简单、快、原子性强；复杂状态机由后面的数据库订单状态和 Redis 回补逻辑共同维护。

## 第三轮：Kafka 异步落库与消息可靠性

### 面试官问题

引入 Kafka 是为了削峰填谷。请描述：成功预扣库存后，你往 Kafka 发送的消息体包含哪些字段？Consumer 如何消费并生成订单？消费者失败后如何处理？

### 标准回答

当前秒杀成功后发往 Kafka 的消息体是 `SeckillOrderMessage`，包含四个核心字段：

- `orderId`
- `userId`
- `voucherId`
- `createTime`

Producer 在入口线程里把这条消息序列化成 JSON，发送到秒杀下单 topic，当前 topic 名是 `seckill-order-create`。消息 key 我用的是 `orderId` 的字符串形式。

Consumer 收到消息后，会先做两件事：第一，判断 benchmark 模式下是否人为暂停消费；第二，把 JSON 反序列化成 `SeckillOrderMessage`。然后进入 `createVoucherOrder` 这个核心方法。这里我会先按 `userId` 拿一个 Redisson 锁，防止同一个用户并发落库。接着查数据库中这个用户这张券是否已经有订单：

- 如果没有订单，就扣数据库库存、插入一条 `UNPAID` 订单、记录创建时间和更新时间
- 如果有一条 `CANCELLED` 订单，而且 ID 和这次消息里的 `orderId` 一致，就走重激活分支，把订单状态改回 `UNPAID`，并清掉 `payTime/useTime/refundTime`
- 如果已经有有效订单，或者状态不匹配，就把它视为重复消息或脏消息直接跳过

订单落库成功后，我会给这笔订单再投递一个超时关单消息到 Redisson 延迟队列。这样就把“抢到资格”“异步落库”“超时自动关单”串成了一条完整链路。

如果消费端处理失败，当前实现是直接抛异常，让 Kafka 这边继续走重投递，同时在业务指标里把 `consumerFailure` 记下来。因为我消费端做了 Redisson 锁 + 数据库查重 + 唯一约束兜底，所以重复消费不会直接造成多扣库存或多建单。

### 追问回答

#### 追问 1

消息丢失风险怎么控制？Producer 是 `acks=all` 吗？发送失败时用户已经看到“抢购成功”了吗？

当前代码里 Producer 发送消息时是同步 `send(...).get(5, TimeUnit.SECONDS)`，也就是说接口线程会等待 broker 的发送结果。只要这一步成功，说明消息至少已经被 broker 这边确认了。你问到 `acks=all` 这个点，我在配置层是按高可靠思路配的，但我更愿意老实讲当前真实重点：代码层确实是在等发送结果，不是 fire-and-forget。

不过这里有一个很重要的现实问题：即使发送失败，当前接口也不一定立刻返回“抢购失败”。因为我的实现是 Lua 成功后先注册 pending-send，再尝试发 Kafka。如果 Kafka 首发失败，我会记录失败指标并保留 pending，由后台重试任务继续补发。所以对用户来说，他拿到的是“抢购请求已被受理”的结果，而不是“订单已经稳定落库”的结果。这其实就是典型的最终一致性口径。

如果面试官继续追问，我会主动承认：当前这种实现更偏“保证消息最终送达和资格不黑洞”，而不是强一致地告诉用户“只有消息进了 broker 我才返回成功”。如果我要进一步收紧用户感知，可以把接口文案从“抢购成功”改成“抢购请求已受理”，再配前端轮询订单状态。

#### 追问 2

Kafka 重复消费怎么保证幂等？数据库唯一键是什么？

我这里是三层幂等保护。

第一层是消费前按 `userId` 加 Redisson 锁，避免同一用户消息被多实例并发处理。  
第二层是消费逻辑里主动查数据库，看 `user_id + voucher_id` 这对组合是否已经存在订单，并根据订单状态判断是新建、重激活，还是直接忽略。  
第三层是数据库唯一索引兜底，当前表上保留了 `tb_voucher_order(voucher_id, user_id)` 唯一约束，所以即使前两层极端情况下失效，数据库也不会允许同一用户同一张券插入两条有效订单。

所以这里真正的业务幂等键不是订单号，而是 `voucher_id + user_id`。`orderId` 更多是用来关联这一轮请求、支持取消后复用原订单。面试时我会特别强调这一点，因为很多人会误以为“只要订单号唯一就够了”，但秒杀的一人一单约束本质上是按“用户 + 券”活动维度建模的。

#### 追问 3

如果 500 个成功请求全进入 Kafka，但 Consumer 只有 1 个，积压会越来越严重，用户迟迟收不到结果，怎么办？

这个追问其实正好问到了我当前架构的短板。是的，在我现在这套单机、单 broker、单 partition 的配置下，Consumer 确实只有单通道，消息积压一旦放大，用户拿到最终订单结果的时间会被拉长。所以我不会回避这件事。

我现在的处理方式有两层。第一层是可观测性，我在 benchmark 里专门埋了 `mqBacklogPeak`、`mqDrainCompletedAt`、`pendingRetried`、`consumerFailure` 这些指标，压测时会观察 backlog 峰值和最终 drain 时间，而不只盯接口 QPS。第二层是链路容错，即使短时间积压了，最终也要保证消息可排空、库存与订单一致、pending-send 可补偿。

但如果真要往更强的工程化方向走，我的优化顺序会很明确：先把 Producer 从同步 `get()` 改成真正异步，再把 Kafka 从 `1 partition` 提到 `2/4 partition`，同时给 Consumer 配并发。因为当前瓶颈不在 Redis 入口，而在“成功请求的异步后半段链路”。

### 如果继续深挖，我会主动补充

我会主动加一句：这个项目里 MQ 的价值不是“凭空把总工作量变小”，而是把“同步写库压力”变成“后台可排队、可补偿、可恢复的异步工作流”。这句话非常关键，能帮助面试官理解为什么我不硬吹它的本机吞吐一定最高。

## 第四轮：自动关单与库存恢复（Redisson + Spring Task）

### 面试官问题

你提到基于 Redisson 延迟队列 + Spring Task 兜底实现自动关单，关单后自动恢复库存及购买资格。详细解释一下这条链路。

### 标准回答

这条链路我拆成“主路径”和“兜底路径”两部分。

主路径是 Redisson 延迟队列。当前实现不是我自己手写 ZSet 轮询，而是用了 Redisson 的 `RDelayedQueue` 套 `RBlockingDeque`。订单创建成功后，我会构造一个 `OrderTimeoutMessage`，里面带 `orderId`、`userId`、`voucherId`、`expireAt`。然后根据 `expireAt - now` 算出延迟毫秒数，调用 `delayedQueue.offer(json, delay, TimeUnit.MILLISECONDS)` 把它放进延迟队列。后台有一个单线程消费者线程池一直在 `blockingDeque.take()`，拿到到期消息后就调用 `closeTimeoutOrder(orderId, "DELAY_QUEUE")`。

兜底路径是 `Spring Task` 定时扫描。它按固定频率去扫数据库里 `status=UNPAID and create_time < now - timeoutDuration` 的订单，每次按 batch 扫一批，默认上限是 `100`。如果延迟队列漏掉了、Redis 抖动了、消费线程异常了，扫表任务还能把这些超时订单补关掉。

真正关单的核心逻辑在 `closeTimeoutOrder`。它会先查订单是否存在，然后用带状态条件的更新把订单从 `UNPAID` 改成 `CANCELLED`。只有更新成功，才继续往下做两件事：第一，数据库库存 `stock + 1`；第二，调用 Redis 回补脚本，把 `seckill:stock:{voucherId}` 加回去、把用户从 `seckill:order:{voucherId}` 集合里删掉，并写入 `seckill:reorder:{voucherId}:{userId}=orderId`。这样用户后续就能再次抢购，而且会复用原订单号。

这个设计的关键点在于：是否能关单，不是靠分布式锁强行串行，而是靠订单状态 CAS。谁先把 `UNPAID` 改掉，谁就拿到状态变更权；另一个并发操作更新行数为 0，就知道自己失效了。

### 追问回答

#### 追问 1

你压测里 `P95 4055ms -> 533ms` 这个延迟是什么含义？对比的是什么方案？

这个 `P95` 指的是“订单理论到期时间”到“关单真正完成时间”的延迟，不是从创建订单开始算到被关闭的整个生命周期。当前指标是通过 `expireAt = createTime + timeoutDuration` 算出来的，然后在关单成功那一刻记录 `now - expireAt` 的 lag。

对比的是两种模式：

- `FALLBACK_ONLY`：只靠 `Spring Task` 扫表
- `DELAY_QUEUE_FALLBACK`：Redisson 延迟队列为主，Spring Task 为兜底

在统一的 `100 单 / 15 秒超时` 场景下，前者 `P95=4055ms`，后者 `P95=533ms`。之所以纯扫描会更慢，很容易理解：定时任务不是在订单到期瞬间触发，而是按扫描周期去发现超时订单，所以天然存在一段额外等待时间；而延迟队列能更贴近订单到期点触发。

#### 追问 2

关单恢复库存时，是否重新执行 Lua 校验？用户再次抢购时，Lua 怎么知道他曾经抢到过但订单已关闭？

当前恢复库存时不会重新执行 Lua 校验，因为这一步不是“重新申请资格”，而是“把之前占掉的资格释放出来”。我这里是通过回补脚本直接修改 Redis 结构：

- `INCRBY seckill:stock:{voucherId} 1`
- `SREM seckill:order:{voucherId} userId`
- `SET seckill:reorder:{voucherId}:{userId} orderId`

所以当用户下次再来请求时，Lua 里 `SISMEMBER` 检查到这个用户已经不在下单集合里了，就会允许他再次通过资格校验。与此同时，Java 代码在执行 Lua 之前会先去读 `reorderKey`，如果里面有值，就说明这个用户之前抢到过但订单被取消了，这次不新生成订单号，而是复用原来的 `orderId`。这就是我维护这个状态机的方式。

#### 追问 3

如果 Redisson 延迟队列因为 Redis 宕机丢消息，Spring Task 兜底怎么做？扫表会不会压力大？

当前兜底方案就是扫表。具体条件是查 `status=UNPAID` 且 `create_time < now - timeoutDuration` 的订单，然后分页批量处理。默认不是全表一次扫穿，而是每次 `LIMIT timeoutScanBatchSize`，当前 batch size 是 `100`。

它当然不是零成本的。订单量特别大时，扫表会给数据库带来压力，所以我不会把它包装成“完全没有问题”。但当前这个项目的定位是单机本地高并发秒杀演进，兜底扫描的角色是“低频兜底”，不是主路径高吞吐调度器。主路径还是 Redisson 延迟队列，扫表只是防止漏关单。

如果继续工程化，我会进一步做两件事：一是确保这张表上有适合 `status + create_time` 的扫描索引；二是如果业务再扩大，考虑把超时处理迁移到更成熟的延迟消息体系，而不是长期依赖扫表兜底。

### 如果继续深挖，我会主动补充

我会主动强调支付和关单并发时为什么没用悲观锁。因为这个问题的本质只是单条订单状态竞争更新，用 `status=UNPAID` 条件更新就能做成轻量级 CAS，没有必要引入重量级串行锁。

## 第五轮：缓存异常防护（布隆过滤器、缓存击穿、一致性）

### 面试官问题

你说纯非法请求场景下，数据库回源次数从 26 次降到 0。非法请求指什么？布隆过滤器拦截的是什么？怎么预热？

### 标准回答

这里的非法请求，不是说参数格式非法，而是指“请求了一个业务上不存在的 shopId”。我在压测里固定用的是 `shopId=99999999`，也就是一个根本不存在的商户 ID，目的就是专门观察缓存穿透防护链路。

我当前布隆过滤器拦截的是不存在的商户 ID，不是秒杀券 ID。实现上用的是 Redisson 的 `RBloomFilter<String>`，名字默认是 `bf:shop:id`。项目启动后它会调用 `tryInit(expectedInsertions, falseProbability)`，当前配置是：

- `expectedInsertions = 100000`
- `falseProbability = 0.03`

如果当前过滤器里还没数据，我会调用 `rebuild()`，把数据库里现有的所有商户 ID 全量刷进布隆过滤器。也就是说，它的预热方式是“按真实商户表全量重建”，不是手工一个个 add。

然后查询链路里走的是 `queryWithBloomPassThrough`。它先用布隆过滤器判断这个 ID 可能不存在还是可能存在：如果明确不存在，就直接返回空，不走 Redis、不走数据库；如果可能存在，再走普通的 pass-through 流程，也就是先查 Redis，没命中再回源数据库，数据库也没有的话再写一个空值缓存。

所以这套组合不是“只有布隆过滤器”，而是“布隆过滤器挡掉明显不存在的数据，缓存空值兜住漏过去的请求”。

### 追问回答

#### 追问 1

缓存击穿用的是逻辑过期，具体怎么实现？多个线程同时发现过期怎么办？

逻辑过期的实现是我在缓存值外面再包一层 `RedisData`，里面包含两部分：

- `data`
- `expireTime`

查询时如果发现 `expireTime` 还没到，就直接返回旧值；如果已经过期，也不是马上删缓存，而是先尝试拿一个互斥锁 `lock:shop:{id}`。拿到锁的线程会异步提交一个缓存重建任务，去查数据库并刷新逻辑过期时间；没拿到锁的线程不会阻塞等待，而是直接返回当前缓存里的旧值。

这样做的目的是避免热点 key 一过期就一堆线程同时打 DB，也就是典型的击穿问题。代价是这是一种“读旧值换可用性”的方案，不是强一致读。对于商户详情这种业务，这个权衡是合理的。

#### 追问 2

缓存与数据库最终一致性怎么保证？你是先更新 DB 还是先删缓存？如果删缓存和写库之间有并发读怎么办？

我这里采用的是典型的旁路缓存思路，优先保证数据库是最终事实源，所以更新路径是“先更新数据库，再删缓存”。原因很简单，如果先删缓存再写库，在这两个动作之间一旦有读请求进来，它可能把旧数据重新回源写回缓存，导致脏值复活。

当前项目里我针对“删缓存失败”又补了一层 Kafka 补偿重试，也就是把需要重试删除的缓存 key 作为消息再投递出去，后台消费者继续删；如果极端情况下这层也失败了，还有 TTL 兜底，保证脏缓存不会无限期存在。

如果面试官继续深挖“那先更新 DB 再删缓存也不是强一致”，我会明确回答：对，当前方案保证的是最终一致性，不是严格强一致。这个项目的取舍是业务可接受短暂延迟，但不能接受高并发下为了强一致把读链路做得特别重。

#### 追问 3

缓存空值过期时间设多久？恶意请求大量不存在的商品 ID，会不会把 Redis 塞满？

当前空值缓存 TTL 是 `2` 分钟，定义在 `RedisConstants.CACHE_NULL_TTL = 2L`。这个时间不会设得很长，因为空值本身只是为了抵御短时间重复穿透，不希望把“不存在”这个结论在缓存里保留过久。

至于你说的“攻击者请求海量不同不存在 ID，会不会把 Redis 塞满”，只用空值缓存确实会有这个风险，所以我才用了布隆过滤器 + 空值缓存的组合。对那些明显不在布隆过滤器里的 ID，我根本不会落 Redis 空值；只有“布隆误判成可能存在”或者防护关闭时，才会走到空值缓存这条链路。再往上走，如果真要扛大规模恶意刷接口，还需要网关层限流、用户/IP 维度限流、验证码或风控，而不能只靠缓存层。

### 如果继续深挖，我会主动补充

我会主动补一句：当前布隆过滤器误判率是 `3%`，所以它的风险不是“把不存在的数据放过”，而是“把少量合法数据也误判为存在”。但它不会把合法 ID 判成不存在之外的错误结果，因为布隆过滤器只会产生假阳性，不会产生假阴性。所以真正需要防的，是“误判导致多走几次缓存或 DB”，而不是“合法数据被完全拦死”。

## 第六轮：压测与监控

### 面试官问题

你说做过压测，用的是 JMeter 还是其他工具？关注了哪些指标？有没有发现系统的最短板在哪里？

### 标准回答

压测工具我用的是 `JMeter 5.6.3`，但不是裸跑。我外面又包了一层 PowerShell runner，用来做以下事情：

- 每轮场景前重置 MySQL、Redis、MQ backlog 和 benchmark 指标
- 调用 `/benchmark/admin/**` 切换缓存穿透模式、timeout 模式、consumer pause
- 跑完后等待异步链路 drain，而不是只看 JMeter 停止时的瞬时结果
- 汇总 JTL、业务指标、数据库最终库存和订单数

所以我关注的不只是 HTTP 吞吐，还包括四类指标：

- 接口层：`QPS`、`Avg`、`P95/P99`
- 业务层：`ApiAccepted`、`luaStockRejected`、`consumerCreated`、`timeoutClosed`
- 异步链路：`pendingRegistered`、`pendingRetried`、`mqBacklogPeak`、`drainCompletedAt`
- 最终正确性：`FinalStock`、`FinalOrders`、`DuplicateUsers`

压测完以后，我认为当前系统最短板已经比较明确了，不在 Redis 前置资格校验，而在“成功请求的后半段异步链路”：Producer 还是同步 `send().get()`，Kafka 是单 broker + 单 partition，Consumer 也是单通道去做完整事务，所以只要成功请求数量一放大，瓶颈就会出现在 MQ 消费和最终 MySQL 落库上。

### 追问回答

#### 追问 1

Redis 在 5000 并发下 CPU 使用率多少？Lua 平均耗时多少？有没有开 pipeline 或连接池优化？

这里我不会编一个我没正式采到的 Redis CPU 数字。当前正式压测里我重点采的是业务指标、JMeter 结果、MySQL 运行态和 MQ drain，没有把 Redis CPU 和单次 Lua 精确耗时作为主报告指标，所以这个地方我会老实回答：没有拿到足够稳定的 Redis CPU 和 Lua 单次耗时结论，不会硬报数。

但从实现形态看，当前 Lua 脚本逻辑非常短，只做 `GET`、`SISMEMBER`、`INCRBY`、`SADD` 这几步，没有复杂遍历，也没有 pipeline 这种跨请求批处理优化，因为 Lua 本身已经把这一批 Redis 操作收敛成原子执行了。连接池方面用的是 Spring Data Redis 默认连接管理，我没有额外做像 pipeline 批量提交那种专门优化，因为当前瓶颈并不在 Redis 多次往返，而在异步后半段。

#### 追问 2

成功请求只有 500 个，Kafka 压力不大。如果库存扩大到 5000，Kafka 会不会成为瓶颈？做过更大规模压测吗？

会，而且我认为它很可能会成为当前架构的主瓶颈。原因很直接：现在 Kafka 只有 `1 partition`，Consumer 也是单通道，而且每条消息背后都要走数据库扣库存、查重、建单、投递关单消息的完整事务。如果库存从 `500` 扩到 `5000`，那通过 Lua 进入成功链路的请求就会更多，Kafka backlog 和 MySQL 落库压力都会显著上升。

更大规模的正式压测我没有把它做成当前报告的主结论，因为这套单机单 partition 环境本身并不适合拿来证明 Kafka 横向扩展能力。对我来说，这一版压测的重点是先证明链路正确性、可补偿性和最终一致性。如果继续优化下一轮，我会专门做 `2/4 partition` 敏感性实验，再看 Producer 异步发送和 Consumer 并发之后能把成功链路吞吐抬到什么程度。

#### 追问 3

异步落库时，MySQL 的写入 TPS 能到多少？有没有出现死锁或行锁等待？

当前正式报告里没有把 MySQL TPS 单独做成 headline 指标，所以我不会硬给你一个写入 TPS 数字。更准确的说法是：从压测现象看，成功请求一多，最终仍然要回到 MySQL 做库存扣减和订单写入，所以它是整个系统的最终事实瓶颈。

至于死锁和行锁等待，当前单机压测里我没有遇到严重死锁导致链路崩掉的情况，主要因为入口已经把绝大多数失败请求挡在了 Redis 层，真正落到 MySQL 的成功请求量被压缩到库存量级。但如果库存扩大、成功消息量显著增加，MySQL 热点写竞争肯定会重新变得更明显，所以我才会说当前架构下一步的重点不是继续抠 Redis，而是要优化 Kafka 并行度和成功链路落库吞吐。

### 如果继续深挖，我会主动补充

我会主动补上压测参数设计逻辑：`flash-burst` 用 `1000` 线程、`3` 秒 Ramp-Up、`10` 秒持续，是为了模拟活动开场洪峰；`flash-sustain` 用 `500` 线程、`5` 秒 Ramp-Up、`60` 秒持续，是为了观察持续承压下的 Redis 过滤、Kafka 积压和最终 drain。这能体现我对压测设计不是只会跑工具，而是理解为什么这样设。

## 第七轮：异常与边界场景

### 面试官问题

请思考几个异常场景：Redis 主从切换、Kafka broker 宕机、用户主动取消支付。系统会怎么表现？

### 标准回答

这部分我会区分“当前方案已有机制”和“真正高可用还缺什么”，不会把单机项目说成生产级容灾架构。

### 追问回答

#### 追问 1

Redis 主从切换导致部分预扣数据丢失，用户再次请求会怎样？会不会超卖？

如果 Redis 是异步主从复制，在主节点执行完 Lua 但从节点还没同步到的时候主节点宕机，确实有可能出现资格标记和库存预扣数据丢失。这种情况下新主节点会认为部分用户从未抢到过，用户再次请求就可能重新通过资格校验。这个问题不是我当前项目已经彻底解决的，我会明确承认它是 Redis 异步复制架构下的一类经典一致性风险。

但它不一定直接导致数据库层超卖，因为我后面还有 MySQL 库存扣减和订单唯一约束兜底。也就是说，Redis 层的状态可能会临时不一致，但数据库层仍会尽量拦住最终错误结果。不过用户体验会变差，系统也可能出现资格重复发放、补偿更复杂等问题。

如果要往真正高可用方向补，我会考虑两条路线：一是 Redis 层提高复制可靠性和切主策略，二是把资格预占和最终事实收敛的关系设计得更严格，比如引入更强的一致性写策略或更完整的重放与对账机制。

#### 追问 2

Kafka broker 宕机，Producer 超过重试阈值发送失败，但前端显示成功，怎么补偿？

这正是我现在 pending-send 机制存在的意义。当前流程是 Lua 成功后先注册 pending-send，再发 Kafka；如果发送失败，我不会立刻把这次请求从系统里“忘掉”，而是由定时任务继续轮询 pending-send 做重发。只有当重发次数超过阈值，并且数据库确认没有形成有效订单时，才会回滚 Redis 资格和库存。

所以它的补偿逻辑不是“消息没发出去就认栽”，而是“先重试补发，彻底失败再回滚资格”。这能避免用户看到成功但后台完全没有痕迹。

#### 追问 3

用户主动取消订单，是否恢复库存和资格？和自动关单逻辑是否复用？

当前项目里最完整落地的是“超时未支付自动关单后恢复库存和资格”。如果是用户主动取消支付，从业务语义上我认为也应该复用同一套状态机：先确认订单还处于可取消状态，再把订单状态改为取消，再回补 DB 库存、Redis 库存和购买资格。

但我会老实说明：当前正式压测和报告重点验证的是自动关单链路，用户主动取消不是这轮 benchmark 主场景。所以回答时我会说，现有实现已经具备这套回补原子逻辑，业务上完全可以复用到“主动取消订单”场景，但这部分不是本轮项目最核心的验证重点。

### 如果继续深挖，我会主动补充

我会主动强调：当前项目更偏“最终一致性 + 补偿恢复”思路，而不是“任何中间件异常都不产生中间态”。这个表述更真实，也更符合秒杀项目的工程特点。

## 第八轮：技术深度拷打

### 面试官问题

你提到了 Redisson 延迟队列、布隆过滤器、Kafka 等，我想听你解释底层原理。

### 标准回答

这类问题我会控制在“说清楚原理，但不背源码细枝末节”的粒度。

### 追问回答

#### 追问 1

Redisson 的 `RDelayedQueue` 底层怎么工作？到期是 Redis 回调还是客户端取？

我当前代码用的是 `RDelayedQueue<String>` 配合 `RBlockingDeque<String>`。业务上调用 `offer(message, delay, TimeUnit.MILLISECONDS)` 时，Redisson 会先把消息按“到期时间”管理起来；等消息到期后，再把它转移到底层的阻塞队列里。我的消费线程不是被 Redis 主动回调，而是本地线程池一直在 `blockingDeque.take()` 阻塞等待，所以本质上仍然是客户端消费模型，不是 Redis 主动推回调给我。

如果面试官非要追到更底层，我会说它背后本质上依赖的是 Redis 的有序结构加就绪队列思路，而不是 Redis 原生提供“延迟消息服务”。Redisson 是帮我们把这一套封装好了。

#### 追问 2

你用的是 `RBloomFilter` 吗？误判率是多少？误判怎么办？

是的，我当前用的是 Redisson 的 `RBloomFilter<String>`。项目里配置的参数是：

- `expectedInsertions = 100000`
- `falseProbability = 0.03`

误判率当前设成 `3%`。这里要先把 BloomFilter 的误判讲清楚：它的误判是“把不存在的数据误判为可能存在”，也就是假阳性，不会出现“合法数据被误判成不存在”的假阴性。所以它不会把一个真实存在的商户 ID 直接拦掉，最多只是让少量本来可以在布隆层挡住的非法请求继续往下走到 Redis 或空值缓存。

#### 追问 3

Kafka 顺序消费怎么保证？同一个秒杀活动的消息需要顺序吗？

当前 Producer 发消息时用的 key 是 `orderId` 字符串，不是 `voucherId`。在现在这套 `1 partition` 的配置下，其实 topic 里天然就是单分区顺序消费，所以这个问题暂时不敏感。但如果将来扩成多分区，我不会强行要求“同一个秒杀活动的所有消息全局严格有序”，因为这个代价太大，反而会牺牲并发吞吐。

对我这个业务来说，更关键的不是全局顺序，而是幂等和最终一致性。也就是说，即使消息乱序到达，只要同一用户的重复消费能被锁和唯一约束兜住，库存扣减和订单状态能最终收敛，系统就仍然正确。所以未来如果要扩分区，我更倾向按某个业务 key 做局部有序，而不是追求整个秒杀活动全局串行。

## 压轴：100 万机器人在秒杀前 30 秒刷接口，系统怎么扛

### 面试官问题

假设秒杀活动开始前 30 秒，突然有 100 万机器人请求刷你的秒杀接口，不同用户 ID 但都是伪造的。你的系统架构会怎样应对？请从限流、防刷、缓存、DB 四个层面说明你现有的机制和缺失的机制。

### 标准回答

如果是这个场景，我会分四层来回答：网关层、Redis 层、业务层、数据库层。

第一层是网关和入口限流。老实说，当前项目里最完整实现的是应用层的 benchmark 身份注入和业务级资格校验，并没有做成一套特别完整的网关级防刷体系。所以面对 100 万机器人，真正生产化还需要加 IP、用户、接口维度限流，必要时配验证码、设备指纹和风控规则。这个我不会硬说当前项目已经全部做完。

第二层是 Redis 层。当前系统已经具备的优势是：即使机器人请求真的打进业务服务，大量请求也会先在 Redis + Lua 层被快速筛掉。只要库存已经抢空，后续请求都会在 Redis 里因为 `stock <= 0` 直接返回，不会继续打到数据库。如果同一个用户短时间重放，同样会被 `SISMEMBER` 拦住。

第三层是业务层。真正通过资格校验的请求才会进入 Kafka 成功链路，成功请求量会被强制收敛到库存量级。也就是说，哪怕入口总请求很夸张，只要 Redis 这一层扛住，大量机器人流量不会等比例扩散到 MySQL 和订单落库流程。当前项目里最核心的削峰价值其实就在这里。

第四层是数据库层。MySQL 不应该直接面对全部机器人流量，它只应该接住经过 Redis 层筛选后少量真正成功的请求。即便如此，我也保留了数据库库存条件更新、用户券唯一约束、订单状态 CAS 这些最终兜底，保证就算上层某些保护失效，也尽量不要出现超卖和重复有效订单。

如果让我总结“当前已有机制”和“缺失机制”，我会这样说：

- 现有机制：Redis + Lua 资格校验、Kafka 异步削峰、数据库唯一约束、订单状态 CAS、缓存穿透防护
- 缺失机制：网关级限流、验证码、人机识别、IP 黑名单、设备指纹、分布式风控、真正生产级 Redis/Kafka 高可用

所以这道题我不会回答成“我当前项目已经能完美扛住 100 万机器人”，而会回答成“我当前架构已经具备业务层和数据库层的削峰思路，但如果真的上到这种量级，最先该补的不是 Lua，而是网关和风控体系”。

### 如果继续深挖，我会主动补充

我会主动加一句：秒杀系统的防刷从来不是只靠业务代码解决的。业务代码更多是在做“最后一道精确资格校验”，而大规模机器人流量最划算的处理方式，永远是尽量在更前面的层次就把它挡掉。

## 高频薄弱点提醒

- 不要说“Kafka 现在就是完全异步的”。当前 Producer 代码里还是 `send().get(5s)`，只能说业务形态是异步落库，但发送动作本身仍有同步等待。
- 不要说“引入 MQ 后吞吐一定高于 db-cache”。当前正式数据不支持这个结论。
- 不要说“Redis 主从切换、Kafka broker 宕机都已经在项目中完整验证”。更稳的说法是：当前有补偿和回滚机制，但真正生产级高可用还需要额外建设。
- 不要把“Lua 预扣成功”直接说成“订单一定创建成功”。准确说法是：Lua 预扣代表拿到了资格，订单最终由 Kafka 消费和补偿链路收敛。
- 不要把 BloomFilter 的误判说反。它是可能把不存在的数据放过去，不会把真实存在的数据误判为不存在。
